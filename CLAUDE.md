# CLAUDE.md

Context for Claude Code when working with this codebase.

## Project Overview

claudecode.nvim — Neovim plugin implementing the same WebSocket-based MCP protocol as Anthropic's official IDE extensions. Pure Lua, zero dependencies.

### Testing

- `mise run test` — run all tests (busted, with coverage)
- `busted tests/unit/specific_spec.lua` — run one test file

## Architecture Overview

### Core Components

1. **WebSocket Server** (`lua/claude_agents/server/`) — pure `vim.loop`, RFC 6455 compliant.
2. **MCP Tool System** (`lua/claude_agents/tools/`) — tools Claude can execute.
3. **Lock File System** (`lua/claude_agents/lockfile.lua`) — discovery files at `~/.claude/ide/`.
4. **Selection Tracking** (`lua/claude_agents/selection.lua`).
5. **Diff Integration** (`lua/claude_agents/diff.lua`).
6. **Terminal Integration** (`lua/claude_agents/terminal.lua`) — internal and external terminals.
7. **Live Cursor** (`lua/claude_agents/live_cursor.lua`) — opt-in ride-along view.
8. **Plan View** (`lua/claude_agents/plan_view.lua`) — plan-mode rendering, on by default.
9. **Terminal Links** (`lua/claude_agents/terminal_links.lua`) — on by default.
10. **Session Persistence** (`lua/claude_agents/session_state.lua`) — opt-in.
11. **Per-Tab Status** (`lua/claude_agents/status.lua`) — on by default.
12. **Agents Mode** (`lua/claude_agents/agents_view.lua`, `lua/claude_agents/agents/*.lua`) — opt-in.
13. **Floating Windows** (`lua/claude_agents/float.lua`).
14. **Launch Profiles** (`lua/claude_agents/profiles.lua`, `launch_settings.lua`, `api_key.lua`, `profile_menu.lua`) — subscription or API key per launch; built-ins on by default, plain launches untouched.

---

A version in parentheses such as `(2.1.300)` is the Claude Code CLI version a CLI behavior was verified against; re-check it when the CLI changes.

### 3. Lock Files

- Lock deleted on `VimLeavePre`; a crash skips that, so `cleanup_stale()` sweeps once per Neovim (from `setup`, before any server claims a port).
- The directory is shared with other editors and users, so the sweep is conservative: `uv.kill(pid, 0)`, and **only an explicit `ESRCH` counts as dead**. `EPERM` = alive but owned by someone else. Unparseable or pid-less locks are left alone. (Erring toward "alive" leaks a file; erring the other way deletes a live editor's lock.)
- Discovery reaches these files only when `CLAUDE_CODE_SSE_PORT` is unset (our server failed to start), in which case the CLI may attach to _another_ editor — hence `terminal.lua` logs an error rather than launching silently in that state.

### 5. Diff Integration

- The unified (inline) provider scrolls the change into view with `center_diff_region`.
- `_measure_diff_region` reads unified.nvim's extmarks for the changed line span **plus deleted lines**, which are virtual lines and therefore invisible to a plain `zz`.
- `_diff_scroll_position` centers the change when it fits the window, else pins its first changed line — with deleted lines above it, via `topfill` — to the top. Applied with `winrestview`; `topfill` is the only way to keep leading virtual lines on screen.
- Shared with the live cursor's edit preview, which renders the same marks.
- **An accepted diff stays up until Claude has written the file.** Claude sends `close_tab` _before_ it writes (2.1.299: once `openDiff` answers `FILE_SAVED`, `close_tab` is sent unawaited and the Edit tool writes afterwards), so tearing down on `close_tab` would put the file's buffer back with its old text until the reload — new → old → new on screen. `close_diff_by_tab_name` → `await_saved_write` polls every `_write_poll_ms` (10) until the accepted text is on disk (line-ending-blind; else a size/mtime/inode change that held still for one poll), then tears down and reloads in one call, which Neovim draws as one change; `_write_timeout_ms` (2s) bounds the wait. A new `openDiff` first takes waiting diffs down (`release_saved_diffs`), or the unified provider would pick the waiting diff's window and lose its proposal when that one restored its buffer.
- **A diff says how to answer it** (`diff._answer_hint`: "Claude|OpenCode wants to change|create <file> · :w accept · :q reject", OpenCode recognised by `[OpenCode]` in the tab name): a window-local `winbar` on the proposal window, a `footer` on a float; a reused editor window's own winbar is saved (`diff_data.saved_winbar`) and restored in `_cleanup_diff_state`. A diff whose proposal window lands in a tab the user is not in (an agent's native diff goes to the agents view's origin tab) is announced with `vim.notify` naming that tab.
- **Focus goes back to the terminal the user was typing in.** Both setups record `float.terminal_mode_window()` (`diff_data.return_win`) before any window moves, and the proposal's tab (`diff_tab`); `_cleanup_diff_state` schedules: that window, `startinsert` — switching tabs only when the user is in the diff's tab (answering an agent's diff in the origin tab takes them back to the agent), never from an unrelated tab. `find_claudecode_terminal_window` (the tab's own terminal) never found an agent's terminal, so an answered agent diff left its terminal in normal mode, where the next keys meant for the agent are E21.
- **A proposal buffer is reported as the file it proposes to change** (`diff.proposal_file`, keyed by `b:claudecode_diff_tab_name`; `selection.reported_path` for every selection, the at-mention check, and `getCurrentSelection`'s answer when no selection has been recorded yet). Otherwise its own name (`✻ [Claude Code] cart.py (…) ⧉ (proposed)`) becomes the CLI's editor context and stays after accepting, since focus returns to the terminal, which reports nothing. Matches the VS Code extension, which sends the `fsPath` of its `_claude_fs_right:` document.

### 7. Live Cursor

- Injects a `PreToolUse` hook at launch via `claude --settings` (user settings untouched). `build_launch_hooks` returns the settings as a table; `launch_settings.apply` merges it with the user's own `--settings` and a profile's into the one file the launch passes (see 14). Hook is `scripts/live_cursor_hook.lua` run as `nvim --headless -u NONE -l` — no shell or POSIX tools, so macOS/Linux/native Windows behave identically.
- Hook reads event JSON from stdin, `sockconnect`s to `CLAUDECODE_NVIM_SERVER`, forwards to `live_cursor.ingest`, stamped with `CLAUDECODE_NVIM_TAB` (launching tabpage, so background-tab Claudes don't preview in the current tab) and, for agents-mode launches, `CLAUDECODE_AGENT_ID` (names the **launch**, not the conversation — see 12).
- `Read` → highlight the read line range. `Edit` → real inline diff via unified.nvim (`show_diff` reconstructs the pre-edit file, calls `unified.diff.show_against_text`); falls back to a line highlight without unified.nvim.
- `Write` → `show_write`. The hook fires _before_ the tool runs, so a file being created does not exist yet; opening the path would show an empty buffer that never fills in. Render `tool_input.content` directly, diffed against the pre-write content: `""` for a new file, else the on-disk text **snapshotted synchronously in `dispatch`** (a deferred read would see the already-written file). Without unified.nvim the content is shown undiffed.
- All snippet/content text goes through `split_lines`, which strips the CR of a CRLF file and the trailing empty element — baselines come from `readfile()`, which already dropped them, so otherwise every line of a Windows file mismatches.
- Suppressed when a review diff owns the file (`diff.is_live_for_file`); the diff calls `live_cursor.on_diff_opened` the instant it opens, dismissing any in-flight preview. A preview and a diff in one window can leave the diff's `acwrite` buffer unable to accept with `:w` (`E676`). `diff.find_main_editor_window` skips the preview split (`claudecode_live_preview` window var).
- Target window: `diff.find_window_closest_to_terminal`, falling back to `find_main_editor_window`.
- **Buffer hygiene**: previewed files opened with `bufadd`/`bufload`; buffers we created are tracked in `state.owned_bufs` (gated on a pre-`bufadd` `bufexists` check, so a file you already had open is never owned) and reaped by `reap_owned` on every `show`/`show_diff`/`show_write`, on idle-close, on `on_diff_opened`, and on `cleanup`. Displayed, currently-active (`last_buf`), or modified buffers are left alone (`force=false`) and retried later; `last_buf` is cleared when the inactivity timer fires and in `on_diff_opened`, so the last file of a burst is reaped too.
- **Preview marker leakage**: Neovim remembers window-local options per (window, buffer) pair, so a window that once wore the preview `winbar` re-applies it when that buffer returns. Three guards:
  - `apply_preview_marker` snapshots the window's own `winbar`/`winhighlight` (`state.marker`); `strip_preview_marker` restores rather than blanks them (`winhighlight` is window-local only and never remembered per buffer, so blanking would drop a user's setting).
  - `swap_preview_buf` strips the marker _before_ `nvim_win_set_buf`, and records `state.preview_buf` _before_ the swap (`BufWinEnter` fires synchronously inside it).
  - `ensure_preview_watcher` (`BufWinEnter`/`WinEnter`/`BufWinLeave`, armed from `setup`) notices anyone else putting a buffer in the preview window and calls `release_preview_window` (restore options, drop the tag, forget the window). Idle close does the same with `handover = true`, which also unowns and lists the buffer shown there.

### 8. Plan View

- Renders Claude's plan-mode plan in an editor split, like the VS Code extension. Claude presents plans via its built-in `ExitPlanMode` tool (internal to the CLI, never sent over MCP); `tool_input.plan` carries the markdown.
- Rides the **same launch hook** as Live Cursor: `build_launch_injection` adds `ExitPlanMode` to the `PreToolUse` matcher and a `PostToolUse` entry scoped to it whenever the plan view is enabled, even if Live Cursor is off.
- `live_cursor.dispatch` routes `PreToolUse(ExitPlanMode)` → `plan_view.show`.
- Takes over the editor window closest to the Claude terminal (`diff.find_window_closest_to_terminal`, which uses `find_main_editor_window` for suitability and `_closest_rect_index` for geometry), recording the displaced buffer/cursor and restoring on resolve. The host window is tagged `claudecode_live_preview` so review diffs skip it. Only with no reusable editor window does it create a split (closed, not restored, on resolve).
- Dismissed on `PostToolUse(ExitPlanMode)` (accepted) or the next tool event of any kind (covers reject → replan and accept → execute) → `plan_view.close`.
- Tab-aware via `CLAUDECODE_NVIM_TAB`. Falls back to the longest string in `tool_input` if `plan` is renamed.

### 9. Terminal Links

Click a file path in the Claude terminal to open it in the editor (VS Code parity) instead of the OS file explorer.

- Claude renders file references as OSC 8 hyperlinks with `file://` URLs, but inside `:terminal` clicks go to Claude, which shells out to the OS opener; Neovim has no built-in "open hyperlink on click".
- A `TermRequest` autocmd records the **set of linked file paths** for the terminal (`_url_to_path` handles absolute and the relative `file://name` form Claude emits for cwd files).
- **No screen coordinates are tracked**: Claude's TUI repaints/scrolls links to rows that no longer match where the OSC 8 fired, so a geometry lookup misses real clicks.
- A buffer-local `<LeftMouse>` map opens on **release** (opening on press races the trailing `<LeftRelease>`, which then starts a stray visual selection). `_resolve_click` matches the filename token under the cursor against captured paths — exact, `/<token>` suffix, or a long substring (wrapped path chunks). A bare word matching nothing is left for Claude; non-link clicks are re-fed so Claude's mouse UI keeps working.
- Opens in the window closest to the terminal (`diff.find_window_closest_to_terminal`), jumping to `:line`. Normal-mode `gf` does the same for the path under the cursor.
- Enabling also sets `'mousemoveevent'` so Claude's hover underline works.
- Config: `terminal_links = { enabled, click, key = "gf", mouse_motion }`.

### 10. Session Persistence

`session_persistence = "off"|"global"|"external"`. Restores each tab's Claude _conversation_ when a saved Neovim session loads.

- Every launch is stamped with a conversation id we choose: `terminal.get_claude_command_and_env` appends `--session-id <uuid v4>` (`utils.random_bytes`, shared with the lockfile token). Later starts use `--resume <uuid>`.
- `launch_args` is idempotent per tab (terminal toggles rebuild the command) and stands down when the command already picks a conversation (`-r`, `-c`, `--session-id`, `--fork-session`, `--from-pr` — checked against the whole command, so `terminal_cmd = "claude --continue"` is respected).
- The id is corrected by the launch hook: a `SessionStart` entry is added to `build_launch_injection` even when live cursor and plan view are off (an empty `PreToolUse` matcher would match every tool, so that entry is omitted instead). `dispatch` feeds every payload's `session_id` to `note_session_id`, making the reported id authoritative after `/clear` or a manual resume.
- **The module does no file I/O.** `capture()`/`restore()` exchange a versioned plain table:
  - `"global"` mirrors it into `g:CLAUDECODE_SESSION` (`:mksession` writes it when `'sessionoptions'` has `globals`; re-applied on `SessionLoadPost`).
  - `"external"` leaves storage to auto-session's `save_extra_data`/`restore_extra_data` or the shipped resession extension (`lua/resession/extensions/claudecode.lua`).
- Tabs are keyed by **tab number**, not tabpage handle: handles are not stable across restarts and `:mksession` cannot save tab-local vars.
- Restore is **lazy** — tabs are armed (`pending`) and the CLI starts on that tab's next terminal toggle, so N restored tabs are not N processes at startup. `open_pending` (`:ClaudeCodeSessionRestore!`) forces the eager path.
- `:ClaudeCodeSessionRestore` re-reads the `"global"` payload unconditionally but never gates the rest on that result — in `"external"` mode the session manager has already armed the tabs. Reports `pending_count()` without `!`. Bound to `<leader>aR` only when persistence is not `"off"`.
- A pending id is dropped rather than resumed if the tab's cwd changed, or if no transcript exists — globbed as `<CLAUDE_CONFIG_DIR|~/.claude>/projects/*/<id>.jsonl`, which sidesteps the CLI's undocumented slug rule since ids are unique. A tab with a live record is never retargeted.
- **Only ids the CLI wrote a transcript for are persisted** (`persistable_id`, applied in `capture()`): a minted id is a name, not a conversation, and `--resume` on it fails. A record also carries `fallback`, the tab's last id that did exist, set wherever a record is replaced (a fresh mint in `launch_args`, `note_session_id` after `/clear` or manual resume). A tab with neither is left out of the payload entirely.
- `forget()` deletes the whole record, fallback included. It is called when Claude's process ends while Neovim is still running, so a conversation the user closed is not restored.
- Telling "user closed it" from "Neovim exited": on exit Neovim fires `VimLeavePre`/`VimLeave` **before** `TermClose`, so a `TermClose` while `M.state.shutting_down` is unset is the user's doing. `TermClose` is used rather than provider exit hooks because during shutdown the job's `on_exit` never runs (and snacks only registers `TermClose` when `auto_close` is on). `TermClose` reports only a buffer and a hidden terminal is in no window, so `terminal.tag_terminal_tab` stamps `b:claudecode_tab` after **every** provider call that can start a process (`open`, both toggles, `ensure_visible` — `:ClaudeCode` is a toggle), and only when the call produced a new buffer. The same stamp drives status's `note_launch`. A profile switch's restart (`terminal.is_restarting`) is not a close either.
- The **external** terminal provider has no terminal buffer and therefore no `TermClose`, so those Claudes are still restored.

### 11. Per-Tab Status

`status = { enabled }`. Publishes each tab's Claude as `busy` / `waiting` / `idle` / `none` for tablines, statuslines and third-party plugins. The MCP WebSocket only carries editor actions, never conversation state, so this rides the **same launch hook** and folds lifecycle events into a state machine (`note`):

- `UserPromptSubmit`/`PreToolUse`/`PostToolUse`/`PreCompact` → busy
- `PreToolUse(ExitPlanMode)` → waiting (a plan is on screen)
- `PermissionRequest` → waiting (fires as any prompt goes up, AskUserQuestion included)
- `Notification` → waiting with its message, **unless** it is the "waiting for your input" idle nudge (that is a timer, not a question)
- `Stop` → done or idle; `SessionStart`/`SessionEnd` → idle/none
- `StopFailure` → done or idle, like `Stop`: it fires **instead of** `Stop` when an API error ended the turn (rate limit, no credit, rejected key) (2.1.300). Registered with the status hooks; without it such a turn stays busy.

Rules:

- **A question belongs to the thread that asked it** (`status.advance`, shared with the agents model). Every subagent — background ones included — reports under the conversation's `session_id`, told apart only by `agent_id` (absent on the main thread) (2.1.284). A background subagent's `Pre`/`PostToolUse` while the conversation's own AskUserQuestion is up is not the answer; conversely the main thread can `Stop` while a subagent's prompt is up. So a waiting record carries `questions` keyed by thread (`"main"`, a subagent id) and only that thread moving on ends its question; `SubagentStop` from the asker ends it too (→ busy: its result goes back to the conversation). `PermissionRequest` is the only event naming the asker — it fires ~6s before the `Notification`, which **never** carries an `agent_id` — so it and `SubagentStop` are injected with the status hooks. A question only a `Notification` reported is owned by `"*"` and ends at anyone's next event.
- **A question is about one call, and the thread that asked runs others beside it.** The concurrency-safe calls of one assistant message run together (`Agent`, `AskUserQuestion`, `WebFetch`, `Read`… — read from the 2.1.294 binary; on 2.1.295 both `PreToolUse` land in the same millisecond, and `PostToolUse(Agent)` in the same millisecond as `PermissionRequest(AskUserQuestion)`). So the asker's next event is not the answer: a sibling call (a background `Agent` launch returning, a `WebFetch`) reports while the prompt is still up. A question therefore carries the `id` of its call:
  - Only that call's `PostToolUse` answers it. A sibling's result can arrive at any point during the question.
  - A `PreToolUse` from the asker within `LATE_CALL_MS` is a call that started with the question (hooks are `async` separate processes and race — the question's own call included). Later it is the thread carrying on after a declined prompt, which no hook reports (`PermissionDenied` is the auto-mode classifier's alone); the question's own call is still known by its id however late.
  - **`PermissionRequest` carries no `tool_use_id`** — only the tool and its input, which equals the `PreToolUse`'s. The `PostToolUse`'s input does not: the answer is written into it (`answers`, `annotations`). So `status.identify` remembers the calls in flight (`PreToolUse` → `PostToolUse`, emptied per thread at `Stop`/`UserPromptSubmit`/`SubagentStop`, capped) and pairs a prompt with the newest of its thread, tool and input; a prompt that beat its own `PreToolUse` is paired in `advance` when that arrives. `live_cursor.dispatch` calls it once per event, before either consumer folds it, and only under the status hooks — the live cursor's file-tool matcher sends no `PostToolUse` to forget a call by.
  - The input is kept on the internal record only; `get`/`all` and the autocmd hand out `{ tool, at, id }`.
  - Without ids a call is told apart by tool name.
  - `PostToolBatch` (every call of a message resolved, per thread) would say "moved on" exactly, but costs a hook process per message; not registered.
  - End-to-end check: `WebFetch https://example.com` beside `AskUserQuestion` (its result lands ~1.4s into the question). A background `Agent` launch does not reproduce it reliably: it returns in the same millisecond the prompt goes up, and its `PostToolUse` usually reaches Neovim first, which is the harmless order.
- `done` = "finished but unread". `finished_state` lands a turn in `idle` only when that tab was current **and** Neovim had focus. Otherwise it stays unread until `mark_read` (wired to `TabEnter`/`TabNewEntered` and `FocusGained`, which also restores `set_focused`; `FocusLost` clears it). Reading never clears `waiting`.
- `PostToolUse` is what ends `waiting`: between answering a permission prompt and the tool's result nothing else fires. That is why this feature widens the injected `PreToolUse` matcher to `"*"` and adds a `"*"` `PostToolUse` — a `Bash` call must not read as idle. Cost: a hook invocation (headless `nvim`) before and after every tool call. On by default; `status = { enabled = false }` saves it.
- State is keyed by **tabpage handle** (nothing here outlives the session; handles are never reused), unlike `session_state`.
- `terminal.tag_terminal_tab` calls `note_launch` so a tab counts as having a Claude before its first hook event (never overriding a known state). The `TermClose` watcher in `init.lua` clears the tab when Claude ends.
- Changes emit `User ClaudeCodeStatusChanged` (`data = { tab, tabnr, state, prev, status }`) and, unless `auto_redraw = false`, `redrawtabline`/`redrawstatus`. Repeat events that change nothing user-visible are swallowed. `since` marks when the _state_ was entered (busy→busy tool changes keep it). `get`/`all` hand out copies.

**Spinner / frame clock**

- An icon may be a **list of frames**. `M.SPINNER` reproduces the CLI's spinner: six glyphs `· ✢ ✳ ✶ ✻ ✽` played forwards then backwards (the CLI builds `[...frames, ...frames.reverse()]`, so turning points repeat), one frame per 120ms (`spinner_ms` default), with the last glyph swapped for `✻` when `$TERM` is `xterm-ghostty`. On Windows and in Windows Terminal (`win32`, or `WT_SESSION`/`ConEmuANSI`) `✳` U+2733 is replaced by `✱` U+2731 — U+2733 is emoji-capable and renders coloured/double-width there.
- `icon()` returns the current frame; a `spinner_ms` timer advances it. `sync_spinner` starts/stops that timer from every path that mutates `entries`, so it runs only while something animates, and never under `auto_redraw = false`.
- **There is exactly one timer.** Views a `redrawtabline` cannot reach (the agents view) call `request_frames(name, interval_ms)` to share it, and `status.on_frame(name, fn)` to be called on the tick that _advances_ the frame. It runs at `status.spinner_ms`; a requester may override the rate but does not by default (`agents.spinner_ms` has no default — taking the fastest requested rate would speed up the tabline).
- Stopping the timer does not reset the frame counter; the counter is **global, not per tab**, so every view shows the same glyph.
- `_tick(interval_ms)` marks a timer-driven tick and redraws only when the frame has not already advanced within that interval. `_tick()` with no interval is an unconditional manual step (for tests). `_frame_requests()` reports who holds the clock. `open()` arms through `sync_timers`, not `arm_poll` alone.

**Interrupts**

- **A turn cancelled with `<Esc>` fires no hook at all** — not `Stop`, not `StopFailure` (2.1.221). Without a fallback an interrupted tab stays `busy`.
- The CLI does write `[Request interrupted by user]` into the conversation as a real `user` entry. `agents.transcript` matches it (`INTERRUPT_MARKER`, prefix-matched because tool interrupts append `for tool use`); `_is_interrupt_line` decodes the entry and requires the marker to be the _whole_ message content, because `toolUseResult` entries are `type:"user"` too and a conversation quoting the string would otherwise read as cancelled. `agents.model` calls `note_interrupt` per conversation.
- **Dismissing a prompt with `<Esc>` fires no hook either** (AskUserQuestion, 2.1.284: writes `[Request interrupted by user for tool use]`), so an interrupt also ends a question the conversation's own thread asked (`status.dismiss`) — never a subagent's, whose prompt is not recorded in the conversation's transcript.
- Tab-hosted Claude with agents disabled is covered by `lua/claude_agents/interrupt_watch.lua`, which tails the transcript of a tab an interrupt could change (`status.interruptible`: `busy`, or `waiting` on its own question) for the same marker and calls `status.note_interrupt`. Its clock runs only while such a tab exists, it is **armed at end-of-file** on the transition into `busy`/`waiting` from any other state (so any marker it sees belongs to the watched turn, needing no timestamp bookkeeping; not re-armed between the two, which could step over an unread marker), and a tick is one `uv.fs_stat` per watched tab plus a read of only the appended bytes, capped at 256KB. 500ms tick.
- The agents-side equivalent needs two extra rules: the marker is **stamped with its own timestamp** and only ends a turn that started before it (a transcript keeps every interrupt the conversation ever had), and "already acted on" is keyed by **conversation, not the row** (`refresh_list` replaces row tables every 2s).
- Do not infer interrupts from the keypress: `<Esc>` means many other things in Claude's TUI, and in a turn with no tool calls there is no later event to correct a wrong guess.

### 12. Agents Mode

`agents = { enabled }`, `<leader>aA` / `:ClaudeCodeAgents`. A dedicated tabpage running several Claudes on one project: selected agent's terminal centre, project sessions top-right, that agent's file activity bottom-right, files it touched top-left, the subagents it started bottom-left.

**Transcript store is the source of truth**

- All numbers come from the CLI's own store (`<CLAUDE_CONFIG_DIR|~/.claude>/projects/<slug>/<id>.jsonl`), not our accounting — so they are right even for conversations that ran in another editor.
- `agents/transcript.lua` folds `toolUseResult.structuredPatch` hunks (counting `+`/`-` lines) plus the session name. Name priority: user rename (`{"type":"agent-name","agentName":…}`, last wins) → generated `ai-title` → first user message. The rename must be read on its own: renaming only sometimes rewrites `aiTitle`.
- A `Write` that _creates_ a file records an empty patch, so the whole `content` is counted instead; otherwise every new file reads `+0`.
- Cheap enough to run per tool call because of a **substring prefilter** (`"toolUseResult"` and `"structuredPatch"`/`"file":`) that skips ~99% of bytes before `vim.json.decode`, and because the log is append-only: `offset` (advanced only to the end of the last _complete_ line, so a scan caught mid-write re-reads it) makes an update cost only the new bytes. Cache key is `(size, mtime, ino)` — a shrink or new inode means compaction, and the fold restarts.
- **Not every line is conversation.** The CLI writes records of its API requests beside it (`api-request`, `api-request-shape`, `api-request-blob`; 2.1.300). A blob is a message as it was sent — every tool call again, after its result, with no timestamp, and a subagent's results too — so a raw `"type":"tool_use"` match would fold each call twice and leave the copy `running`. Every record opens with `{"type":"api-request`: `_fold_line` skips it right after counting the line (`_is_request_record`, also used by `subagent_view.fold_line`), `fold_tool_use` takes only `assistant` entries, and `tool_call` only `user`/`assistant` ones (it takes the last line naming the call, which would be the copy). Readers that decode and test `entry.type` (`_is_interrupt_line`, `_task_notification`, `search_entry`) are unaffected.
- **A result is a result without `toolUseResult`.** A print-mode (`entrypoint: "sdk-cli"`) subagent writes none on its ordinary results (2.1.299, 2.1.300; the main thread does). `_fold_line`'s `is_result` is the decoded copy's key **or** an unescaped `"type":"user"` plus `"type":"tool_result"`; otherwise such a result would never settle its call and would be noted as something the user typed. Everything else the fold reads from `toolUseResult` has a text fallback for a bare result, each requiring the result to _open_ with the CLI's own words (2.1.300 print mode): a background shell (`background_from_text`, see Background shells), a monitor (`Monitor started (task <id>, …`), a `TaskStop` (the result object as text, `{\"message\":\"Successfully stopped task: <id> (…`), and a foreground subagent's cost (the `<usage>subagent_tokens: N … duration_ms: N</usage>` closing its hand-back text; the last one, since a report may quote another).

**Slug rule (Windows-critical)**

- The slug is the cwd with every non-alphanumeric character replaced by `-`. Do **not** use `fnamemodify(cwd, ":p")`: its trailing separator gets slugified (`D--proj-` vs the CLI's `D--proj`), which breaks every Windows project.
- Past **200 characters** the slug is cut there and `-<hash>` appended, where `h = h * 31 + unit` over the path's **UTF-16 code units** kept to a signed 32-bit int, then `Math.abs(h).toString(36)`. Code units, not bytes — JS `replace(/[^a-zA-Z0-9]/g, "-")` substitutes one dash per unit, so a two-byte `ö` is one dash and an astral emoji is two.
- Fallback on a slug miss: scan every project directory for a transcript naming this cwd. It must use `_io.read_sync` (bounded, miss-path only) — the asynchronous reader cannot answer in time, and treating "hasn't answered" as "no match" makes a slug miss return an empty list. Match the cwd both raw and with separators escaped the way JSON writes them, case-folded on Windows.

**Worktrees and moved transcripts (`⎇`)**

- **The CLI keys a transcript by the directory its session is _in_, and moves the file when that changes** (2.1.291; one function does the move, called from `EnterWorktree`, `ExitWorktree` and `/cd`). `claude --worktree <name>` writes under the worktree's slug from its first line. `EnterWorktree` mid-session **renames** the transcript out of the project's directory into the worktree's, sidecar directory (`<id>/subagents/…`) included, and `ExitWorktree` moves it back. Enumerating only `projects/<slug(cwd)>/` therefore misses every such conversation: a running one would become the synthetic `New session` row with nothing in any pane, a stopped one would leave the list.
- The worktree is always `<repository root>/.claude/worktrees/<name>` — also for a session started in a subdirectory, whose cwd afterwards is the worktree's root. So `transcript.worktree_dirs` finds the store directories by **slug prefix** (`slugify(<root>/.claude/worktrees/)`, the root from `_repo_root`: the nearest `.git` at or above the cwd) in one `scandir` of the store, which also finds the store of a worktree that has since been deleted. A slug past 200 characters ends in a hash of the whole path and has no usable prefix, so worktrees still on disk are looked up by their exact slug as well. `transcript.list` merges these with the project's own directory, one row per id. **By directory, not by reading `originalCwd`**: every conversation in a worktree of the repository is listed, which keeps the enumeration stat-only. The search's `project` scope gets them for free.
- **Stored under a worktree's slug is not the same as being in one.** Resumed after its worktree was deleted, a conversation carries on in the project (the CLI says so and clears the binding) while its transcript stays where it was. So the mark comes from the transcript: `{"type":"worktree-state","worktreeSession":{originalCwd, worktreePath, worktreeName, worktreeBranch}}`, stamped on entering and leaving and again at the end of every turn (the last one is current), with `"worktreeSession":null` once out. `_fold_line` folds it into `sum.worktree` (`false` = the CLI said none, nil = it never said) ahead of the rewind test, looking only in lines up to 16KB so the test stays off megabyte tool results. `transcript.worktree_of` falls back to the shape of the first cwd (`…/.claude/worktrees/<name>`) **only for a transcript that was never stamped** — a plain `claude` started by hand inside a worktree writes no stamp at all, while a `--worktree` launch that has left still names the worktree in its first message. Mirrored to the warm cache without a version bump: an entry without it reads as never-said, and the first fold corrects it.
- **A row has two directories** (`model.place_of`). `row.cwd` is where it is **resumed**: `worktree.original_cwd`, because `--resume` from there finds the transcript in the worktree's store and puts the session back in the worktree by itself (also with the worktree deleted). `model.selected_cwd()` is what its files are **named from**: the worktree, so a row reads `lua/x.lua` rather than `.claude/worktrees/wt/lua/x.lua`. A file touched outside the worktree keeps its whole path — it is another checkout's file of the same name.
- Drawn as `⎇` (U+2387, one cell, not emoji-capable) after the flag, in `ClaudeCodeAgentsWorktree` (→ `Directory`: it says where the work is and asks for nothing). Only when the worktree is not the view's own directory (`worktree_elsewhere`) — a view opened inside a worktree would otherwise mark every row. The centre's resume notice names it (`⎇ worktree <name> · <branch>`). The same mark sets off a Tasks row for a subagent spawned with `isolation: "worktree"`, whose `meta.json` records `worktreePath` (its transcript stays in the session's `subagents/`).
- **A move under a running row** (`refresh_list`): the listing has the id at another path. `carried_fold` → `transcript.rehome(from, to)` takes the summary along when the file is provably the same one (same inode, not shorter, nothing left at the old path), so the row and the panes read as they did and only the appended lines are folded (`fold_row`). When it cannot be shown, the fold starts over and `reset_seen` makes that a backfill rather than activity. Either way the old path is invalidated and the Tasks pane is pointed at the moved sidecar. A row with no summary yet keeps its previous title and worktree.
- `/cd`, and a worktree a `WorktreeCreate` hook made outside the repository, put the transcript where no rule about the project names it. A live id the listing lacks is therefore looked up by id across the store (`transcript.locate`, through `locate_live`: the last hit re-checked with one `stat`, a miss not asked again for `LOCATE_RETRY_S`) before it is called a new session. It is not listed once stopped — it is that directory's conversation now. (`/cd` was read from the binary, not run.)
- **`git status` answers only for its own working copy**: asked from the project it prints nothing for a file inside a worktree that the worktree itself reports ` M`. `git.status_all` groups paths by `git.root_of` (the nearest `.git`, remembered per directory, forgotten on a manual refresh) and merges one query per working copy; a path no git working copy claims is asked at the view's cwd. Porcelain paths are relative to the repository root, so this also gives correct letters for a view opened in a subdirectory. `root_of`/`_working_copy` call no `vim.fn`: `refresh_git` is reached from the fold's read callback, a fast context.
- `interrupt_watch` forgets the path it resolved for a conversation when a `stat` fails (the transcript moved), so it re-resolves instead of tailing nothing; the offset still holds, since the file moved whole.
- Hook payloads carry `transcript_path`, correct from `PostToolUse(EnterWorktree)` on — but `SessionStart` on `--resume` names the project's path, where no file is. Unused for that reason, and because polling is the default.
- Background task output stays under the **launch** directory's slug in the temp root across a move, so the paths a transcript states remain valid (the CLI re-points the subagent `.output` symlinks itself). The CLI also `git worktree lock`s the worktrees it makes: removing one by hand takes `-f -f`.

**Path handling**

- `utils.normalize_path`/`path_key` (`/` separators, no trailing one, case-folded on Windows) is the key for `git.parse_status` (git answers with `/` separators on every platform while the CLI supplies `D:\Git\proj\x.lua`) and the comparison basis for `render.relative_path`.
- `render.shorten_path` splits on **both** separators, keeping a drive with the folder it names.

**Concurrency and instances**

- Nothing blocks: reads go through `uv.fs_*` callbacks in `_chunk_size` slices, sessions are folded a `fold_batch` at a time newest-first, and a warm cache under `stdpath("cache")` paints real numbers in frame one. Unknown counts show `+· -·`, never blank.
- **Each agent gets its own MCP server** (`claude_agents.start_agent_instance`) — own port, token, lock file. `M.instances` is keyed by opaque instance id, `M.tab_instance` points at a tab's own Claude, and the sender is identified by `claude_agents.request_context` (with N Claudes per tab, "which tab" does not identify the sender). `close_all_diffs` scopes by instance so one agent's routine `closeAllDiffTabs` cannot reject a sibling's pending diff.
- Agents run through `agents/registry.lua`, not the terminal providers (which hold one terminal per tabpage). `bufhidden = "hide"` is what lets a hidden agent keep working; switching is a buffer swap.
- `session_state.disown_tab` keeps the view's tab out of per-tab session bookkeeping.
- **Every buffer the plugin rewrites from a timer or hook RPC has `undolevels = -1`** (`render.paint` sets it on whatever it paints; `live_cursor`'s preview buffer and `plan_view`'s plan buffer set it at creation). Neovim closes an undo block only after a typed command, so writes from callbacks all land in **one** block that `undolevels` (a count of blocks) never trims — each full-buffer replace would keep a copy of the old lines until the buffer is deleted, growing a polled pane without bound. Buffers the user edits (`diff.lua`'s proposed buffers, the search input) keep undo.
- `render.paint` also skips a repaint whose lines and marks equal the last one (copies are kept, not the caller's tables), guarded by `changedtick` so a buffer written by anything else is still repainted. Row payloads are updated either way.
- **A launch never enters a directory that is gone**: a row records the cwd its conversation ran in, and a moved project leaves transcripts naming a missing path — `termopen` refuses such a cwd (`E475`). An unusable recorded path is dropped for the directory the view is attached to. A failed spawn reports the reason it was given.

**Layout and routing**

- Every pane carries `claudecode_live_preview` and the tab is marked `claudecode_agents`, so diffs, previews and the plan view never take one over. The tab declares `t:claudecode_layout_owner = { forbids_split, host = "float", float_module, origin }` — the routing protocol every "where does this file go" decision reads (`diff.resolve_target_window`).
- **The centre pane wears the snacks terminal background** (`Normal:ClaudeCodeAgentsNormal` → `SnacksNormal` → `NormalFloat`; the sidebars keep the editor's own `Normal`), and it is **repainted per buffer swap, not once at build time** — Neovim remembers window-local options per _(window, buffer)_ pair, so `nvim_win_set_buf` hands the window whatever that pair last had, which for a buffer that has never been in the pane is nothing. A paint at build time therefore lasts only until the first agent's terminal replaces the pane's buffer. `paint_center` merges rather than overwrites, since `termopen` appends `StatusLine:StatusLineTerm` as a buffer becomes a terminal; a `BufWinEnter`/`TermOpen` autocmd is the backstop for every path that swaps the pane's buffer, and `show_notice` paints itself because the opening notice is shown before `arm_autocmds` runs.
- `agents.tab_name` names the tab, plus `tab_name_var` for which tab-local variable to write (tablines disagree: `t:name`, tabby's `tab_name`, taboo's `taboo_tab_name`), or a function form handed the tabpage for tablines that rename via a command. Nothing undoes it on close.
- **The view stands down for a Neovim session write** (`close_for_session`, via `session_state.prepare_save`): `:mksession` would record four pane buffers and, with `'sessionoptions'` carrying `terminal`, a `term://` buffer per live agent that Neovim restores by re-running the command. It must happen in the manager's **pre-save** hook (auto-session order is `pre_save` → `mksession` → `save_extra_data`); a `VimLeavePre` autocmd of ours loses the race (the session manager loads at startup, claudecode is lazy-loaded, same-event autocmds run in registration order). The record is therefore taken _before_ the close and held in `pending_capture`, consumed by the first later `capture()`. Only on exit: `v:exiting` is the test (`v:null` normally, an exit code from `VimLeavePre` on); `M.state.shutting_down` cannot help, being set by an autocmd registered after the session manager's.
- `M.close({ keep_tab = true })` takes only our own windows, emptying rather than closing the last one, when the tab holds a window of the user's.
- The `close` key (`q`) goes through `M.ask_close` (`agents/confirm.lua`), naming how many of the tab's agents keep running or, under `kill_on_close`, are stopped — `q` dismisses nearly every other window, so it gets pressed in a pane out of habit. `:ClaudeCodeAgents` (`toggle`) still closes without asking.
- `openFile` from an agent **floats**; a **clicked** terminal link goes to a real editor window in the origin tab and takes you there. Deliberately different: one is the agent's idea, the other is yours.

**Floats in agents mode**

- Diffs and file opens land in cascading floats (`agents/float.lua`, a thin wrapper over `lua/claude_agents/float.lua` — see 13), tagged and titled per agent so several are answerable at once.
- A float records what it is _for_, so `float.close_all(session_id, "open")` dismisses the file a plan was shown in (on `PostToolUse(ExitPlanMode)`) without touching a pending diff.
- The diff float hosts the unified inline provider, so `:w` acceptance and the blocking MCP response are unchanged. The float is recorded on the diff state (`float_window`) so `_cleanup_diff_state` closes it on resolve, **forced** (a rejected diff's buffer is still modified).
- `diff_opts.layout = "float"` needs unified.nvim and warns once when it resolves to the native provider, which needs two real windows.
- **Live cursor and the plan view stand down for agents** (`live_cursor.from_agents_mode`, checked in `dispatch` after status/agents routing and before anything opens a window): every window in the agents tab is a pane. Detected by the tab stamp _or_ `registry.is_live(session_id)`, since the stamp only says where the CLI launched.

**Hooks, status and read-state**

- `source = "auto"` rides the hooks `status` already pays for, else polls transcript mtimes. Hook cost is two headless `nvim` per tool call _per running agent_. Status is on by default, so `"auto"` normally means hooks; polling is what a user with `status.enabled = false` gets.
- Two hooks are registered even under polling: `PostToolUse(ExitPlanMode)` and `SessionStart`.
- **Hooks mode still stats the selected transcript every tick** (`transcript.stale`, one `fs_stat`, no read): a `PostToolUse` hook says the tool returned, but the CLI does not write the tool's transcript line in lockstep with it, and a hook can fail to arrive at all. Re-reading only on hook events would leave Changes and Activity behind until the next event (after a long command, until the end of the turn). The status bullet is unaffected, since it comes from the event itself. **Every running agent's transcript is stat'ed too**, not only the selected one: an agent sitting on a permission prompt sends no hook until it is answered, so the edit it made just before asking would wait for some other agent's event before its row counted it.
- **The CLI itself sometimes holds transcript writes** (2.1.300): usually a call and its result are in the file ~0.1s after the edited file is on disk, but sometimes nothing after the opening lines is written until the CLI exits (the file exists from the first entry; its mtime is the exit). Not tied to the permission prompt or to a first-run trust dialog. Nothing the view can re-read is there to show in that state.
- **So an edit is shown from its hook until the transcript has it** (`transcript.provisional`, from `model.note` on `PostToolUse` of `Edit`/`MultiEdit`/`Write`). The payload's `tool_response` is the very `toolUseResult` the transcript will hold (2.1.300), so it is folded by `fold_result` into a summary of its own per call; `provisional_view` hands the panes its events, per-file counts and totals, which `model.rows`, `model.feed` and `model.changes` add in. It looks like any row, since its data is identical. Released the moment the transcript's fold reaches a result with the same `tool_use_id`; not taken at all when the fold already has it (the hook is a separate process and often arrives after the line was read). A subagent's edit is never taken — it is in the subagent's own transcript, so this one would never confirm it. Dropped in `model.poll` once the agent's process has ended and its transcript reads up to date (`transcript.stale` false), since a held transcript is written at exit at the latest. `<CR>` on such an edit (an Activity row, or a Changes row while the transcript has nothing of the file) opens its patch as text, `(not in the transcript yet)`. Hooks mode only: with status off no `PostToolUse` is sent, and none is added for this. Counts never double: the hook's edit and the transcript's are the same call.
- **Only a launch that reports how a state ends may set one** (`agents_view.note` → `model.note(…, { classify = hooks_report_state() })`): true when status is on or the view wants hooks — the same test `build_launch_injection` makes for the full set (`Stop`, `UserPromptSubmit`, `PostToolUse "*"`). Otherwise the live cursor's file-tool `PreToolUse` still arrives and would mark the row busy with nothing to end it. Unclassified events still mark what to re-read, and the row falls back to running/not running.
- Live state is per **conversation**, not per tab (`status.classify` is extracted so the rules stay shared). `done` takes the same three conditions as the tab rule: the conversation is the selected one, the view's tab is current, and Neovim has focus (`status.is_focused`, exported so the rules cannot drift).
- Clearing `done` needs its own wiring: `model.mark_read` (`done` → `idle`; `waiting` untouched) is called by `model.select` (covers `<CR>` and `<C-n>`/`<C-p>`) and by `agents_view.mark_selected_read` on `TabEnter`/`FocusGained`. `status`'s own autocmds cannot help — its entries are keyed by tab and several conversations share this one.

**Activity pane**

- Lists events **newest first** (`model.feed` reverses the store's order and trims the oldest).
- **Includes calls that touch no file** (`agents/tools.lua`, `agents/tool_view.lua`, `agents/ansi.lua`) — shell commands, searches, subagents. They produce no `filePath`, so the file fold skips them by construction.
- A call and its result are two entries joined by a `toolu_…` id, and the **row is built from the call**, so a command appears when it starts, which is what allows showing it as running.
- Only three of five outcomes are drawn (`…` running, `✗` failed, `⊘` stopped by you); most calls simply work.
- **Failure is `is_error`, never stderr** (stderr is mostly progress output from `git`/`rg` and the like). **A refusal is not a failure.** Every refusal's entry carries `toolDenialKind` (`user-rejected`, `permission-rule`, `automode-blocked`, `automode-unavailable`; written since at least 2.1.260), and only that field names them all — print mode words its refusal "… needs approval", a rule "Permission to use Bash has been denied", the classifier its own. `resolve_tool` reads the field (raw, unescaped), keeping `REJECTION_MARKER` for older transcripts; every kind draws `⊘`, and the subagent float says `declined` for the user's and `denied` for the rest. `"interrupted":true` on the Bash result shape is not usable (it is always `false`).
- `_fold_line` closes out every still-pending call when it sees the `[Request interrupted by user]` marker (see 11); otherwise an interrupted call keeps its "still running" marker forever.
- **The row carries only what it draws** — tool, one-line label, id — and `<CR>` re-reads the pair (`transcript.tool_call`). Payloads are the bulk of a transcript, and the id is an exact prefilter: exactly two lines contain it.
- Row labels are per-tool knowledge (`tools.label`): only `Bash` and `Task` carry a `description`; `Grep` is named by its pattern, `WebFetch` by its URL without the scheme, `TodoWrite` by what is in progress and how many are done — with a field-order fallback so unknown MCP tools still get a readable row.
- Float bodies are too (`tools.body`): `Bash` puts the command above its output with stderr as a **named section rather than an error**; on Windows the CLI calls the same tool `PowerShell` (identical input and `{stdout, stderr}` result), so every shell rule is keyed through `SHELLS` (`$ ` vs `PS> ` prompt, `pwsh` kind), and reader detection also knows `Get-Content`/`gc`/`type` (case-insensitive, skipping value parameters like `-Tail 20`) and `ConvertTo-Json`; a subagent shows the reply the parent received; a file list shows one per line; anything unrecognized is pretty-printed **valid** JSON (commas and all — readers copy it out).
- Command output goes through `agents/ansi.lua`, which turns SGR codes into extmarks against `g:terminal_color_*` (256-colour and 24-bit resolved to hex) and drops what a buffer cannot act on (cursor moves, erases, OSC titles). Subtlety: `gmatch("[^;]*")` yields a trailing empty match read as `0`, which resets every colour immediately after setting it — must be handled.
- **The float names what it shows** (`tools.detect_filetype`). Sniff the **output** (not the command — patches come from `git diff | head`, `log --patch`, a written `.patch`) for `diff --git`, an `@@` hunk header, an `index <sha>..<sha>` line, or a `--- `/`+++ ` **pair** (a lone `--- ` opens a YAML document or closes Markdown front matter) → `diff`, or `git` when `commit <sha>` headers are present. The command is asked only what it alone knows: a file being printed (`cat`/`bat`/`head`/`tail`/`less`, taken from the pipeline's **last** stage) is whatever `vim.filetype.match` says, and `jq` is JSON unless asked for raw text. Everything else gets no filetype — a wrong syntax is worse than none. Only the first `SNIFF_LINES` are read, and only stdout (stderr is progress; the `$ …` and `── stdout ──` lines are ours).
- `.` and `gf` say a tool row is not a file rather than doing nothing, but a float stepping with `<C-n>`/`<C-p>` lands on tool rows too — except a `.`-opened one, which skips them silently.
- `f` (`keymaps.filter`) cycles everything / files only / commands only. The filter is applied while walking events from the newest end, not to a slice (with a filter on, visible rows come from anywhere in history). It lives on the view and dies with it, like the sort criterion. `feed_tools = false` folds none of them.
- `model.feed(visible)` takes the pane height plus slack, since the pane repaints wholesale and its cost must not grow with the conversation. The exception is a row the cursor or a float holds (`keep`, see Navigation) — and **scrolling**: once the user is past the first screen, `feed_visible` asks for a screenful beyond where they are (`feed_reach`: the window's last line or the cursor's, whichever is further), so the list grows under them down to `feed_limit`. Nothing else repaints on a scroll (in hooks mode a quiet agent means no repaint at all), so a `CursorMoved` on the feed buffer and a `WinScrolled` (the wheel moves no cursor) call `on_feed_scroll`, which redraws only when the reach nears `state.feed_drawn` and not once the store ran out (`feed_exhausted`).
- `model.feed` returns `events, ages` as parallel arrays rather than copying events (those are the transcript's own cached tables). Ages come from `model`: `stamp_feed` keys a weak table by the event table itself; the first batch after a selection change is a backfill, so it is aged from **each event's own timestamp** rather than declared old wholesale. `stamp_counts` only calls a count changed when it moved from one already shown.

**Layout sizing**

- `layout.sessions_height` defaults to `0.55`; widths default to `0.23`/`0.23` with the terminal taking `0.54`.
- **Only the sidebars are `winfixwidth`/`winfixheight`; the centre absorbs.** Fixing the centre too leaves Neovim no window to take space from (widening one sidebar would shrink the other).
- `build_layout` clears those flags on the window it splits from (a rebuild starts from a surviving pane that still carries them) and applies sizes **last**, after buffers, tags and winbars. Do not toggle `'equalalways'` around construction — restoring it re-equalises every window.
- **A split opened in the tab and then closed redistributes the panes** (`winfixheight` does not stop Neovim when no unfixed window is available in that column). `remember_sizes` snapshots the three sizes whenever the tab holds nothing but the four panes (floats excluded), and `restore_sizes` puts the snapshot back after any window in the tab closes. A snapshot, not the configured fractions, so a dragged size survives. `sizes_locked` is set the moment a window closes and cleared by the restore, so a redraw landing in that gap does not snapshot the damage.
- Snapshots are taken on `WinResized`, `WinEnter`/`WinLeave`, and from `redraw` — deliberately **not** `WinNew`, which fires after Neovim has already taken the space. A focus change is the last moment the layout is reliably intact.
- **`WinResized` and `VimResized` also repaint** (when the view's tab is current): every row is cut to its pane's width, and a quiet view in hooks mode would otherwise keep rows cut to the old width until the poll's list refresh (`list_refresh_ms`, 2s).

**Fade (`agents/fade.lua`)**

- `fade.lua` owns its defaults **alone**; `config.defaults` deliberately carries no `fade` table, because `fade.opts()` merges applied config over its own and a second copy silently wins.
- A new Activity row is drawn lifted above its own colour (`fade.boost`) and **bold** (`fade.bold`) for `fade.hold_ms` (3s), then walks down through that colour into the pane background over `(steps - 1) × step_ms` (~3s) — one continuous ramp from `lit` to `rest`, collapsing to the pre-boost formula when `boost = 0`. Bold is dropped when the ramp starts.
- **The lift is intensity and weight, never brightness.** `intensify` saturates towards 1 (all the lift for a muted `Comment`, none for a vivid `Directory`) and moves lightness towards a colourful band **only away from the pane background and only if the colour is on the wrong side of it**. Scaling channels towards peak does nothing for a colour already there. Brightening (scale channels to lift the largest, spending the remainder towards white) survives only as the fallback for a hueless colour.
- Saturation can cost legibility (the eye weights blue at a fourteenth of green): the result is walked back up in lightness at its new hue until it is at least as legible as the colour it came from.
- A `+N`/`-N` that moved is drawn lit and ramps back within `flash_ms` (3s), set one step longer than the ramp so it has no flat hold.
- `step_ms` matches `spinner_ms` because that clock samples the ramp; ramp length is set by the step _count_, and 25 steps is what makes a 3s fade a fade.
- The ramp is pre-computed highlight groups, not per-frame `nvim_set_hl` (redefining a group is global). It needs no timer: `redraw` asks `anything_moving` of the rows it drew — an animated status icon (`status.is_animated`) or a fade still ramping (`fade.animating`) — and **releases the frame request otherwise**. The shipped `busy` icon is a single glyph (the spinner is opt-in via `icons = { busy = status.SPINNER }`), so by default nothing animates.
- **A count block is one hue at four strengths** (`fade.count_group`). Rest = the theme's colour at `count_sat` (0.25) dimmed `count_dim` (0.60) towards its own block; block = `count_bg_sat` (0.22) of it, `count_bg_lift` from the pane in lightness; flash = the colour itself on a block at `flash_level` (0.50), text following `flash_text_lift` (0.25) of lightness up at the same hue and saturation. Both the dim and the desaturation are needed on the resting number: at equal lightness a desaturated green and a full one read alike.
- Hue priority: the group's own foreground when it is an actual colour → `Added`/`Removed` (Neovim ships these) → the block's own hue → nothing derived. **The block follows the number, not the theme's `DiffAdd` background**, which is often a different hue (tokyonight-moon pairs a green `Added` with a blue block).
- All four colours are walked in lightness at their own hue until they clear `count_contrast` (4.5:1) on whatever they sit on. That floor also limits how quiet `count_dim` can make a number.
- "Is this a colour" is decided by **channel spread**, not HSL saturation, which runs away at both ends (`#eef1f8` reports s = 0.42 with 4% spread; `#a89984` reports 0.14 of spread and looks grey).
- A near-grey has no hue to intensify (hue 0 is red — saturating would flash it pink) and is brightened instead. The two halves must differ, or a flashed count is _less_ legible than one at rest. `flash_level` and `flash_text_lift` trade against each other: a **lower** `flash_level` buys a more legible number (on a `#005523` DiffAdd, `0.8`/`0.1` gives 1.36:1 vs `0.55`/`0.25` at 2.09:1).
- Every span of an Activity row must carry a group — a span without one falls through to `Normal`, which the fade cannot reach. The `read`/`edit` column uses `ClaudeCodeAgentsKind` (default-linked to `Comment`).

**Sessions pane**

- The cursor is anchored to its **conversation** across repaints, not its line (a re-sort or a new session moves rows under it, and `<CR>`/`x`/`dd` would act on the wrong one). `cursorline` paints a line like the selection, so a cursor left on another row makes that row look selected.
- **A session's bullet is dimmed when it is _not_ running** — the reverse of `status`, which dims `idle` (right for a tabline, where a tab with no Claude draws nothing). `model.rows` paints a not-running row in `ClaudeCodeAgentsStopped` (`agents.highlights.stopped`, linked to `Comment`) and drops the group entirely from a live `idle` one. Other states keep `status`'s groups.
- The selected row carries `❯` in the gutter (`SELECTED_MARK`). Its highlight band is a **character range ending where the counts start**, not a `line_hl_group`: a line highlight composes over character-highlight backgrounds whatever the priorities, which would strip the coloured count blocks on exactly the row you most want to read.
- **`/clear` swaps the conversation id under a running terminal** (2.1.226): `SessionEnd(reason="clear")` for the old id, then `SessionStart(source="clear")` with a brand new one, same process, terminal and socket. `--fork-session` has the same shape. Nothing on disk attributes the new conversation to an agent, so the CLI has to say so:
  - A **launch** gets its own name (`agent_key`, passed as `CLAUDECODE_AGENT_ID`) — the registry's second index, since the first one moves.
  - `SessionStart` is injected whenever agents mode is enabled, even under polling.
  - `registry.rekey` moves the agent: this index, its server instance (`claude_agents.rekey_agent_instance` **renames rather than replaces** — the client is still connected to that port and `request_context.session_id()` reads the instance), and any float on screen (`float.retag`).
  - The selection follows the terminal only when it was on the conversation being left.
  - `term.retired` stops an agent drifting back onto a conversation it left: the two events are separate async hook processes, so arrival order is not the CLI's order. `SessionStart` is exempt (`reclaim`) — that is the CLI stating which conversation it is having now.
  - `model.note_session_change` drops the old conversation's per-agent state (otherwise a spinner sits on a row nothing will report about again).
- **A conversation started here is listed before it exists on disk** (the CLI writes the transcript on the first message). `refresh_list` lists what the registry is running as well as what the directory holds (`registry.live_ids`, one synthetic row per live conversation the enumeration missed), built from the only three known things: id, directory, running. Counts are `0`/`0` (not the unknown placeholder, which would claim they are still being read); dated by `term.started_at` (the launch, or the `/clear` that swapped the conversation; wall clock with its fraction, so two new agents sort in launch order rather than tying and falling through to id order); titled `New session`; `refresh_list` carries a row's previous title across a rebuild so the name does not flicker back to the id prefix. It is rebuilt from `live_ids` every pass, so it is taken over by the enumeration or drops out.
- `M.select` resumes only a conversation that has a row; an id that never got a transcript is claimed with `--session-id` as it was the first time.
- The row is named with `transcript.session_path`, which applies the slug rule directly when `project_dir` finds nothing (the project that matters most is the one the CLI has never run in).
- Cursor anchoring is overridden for one paint whenever the selection moved since the cursor was last placed (`state.cursor_selection`), so the cursor lands on a new row when it appears.
- **Every pane line begins with a blank cell**: word-highlight plugins (mini.cursorword, vim-illuminate) otherwise light up every row sharing a timestamp or status letter with the cursor's column-1 word. All of them stand down over whitespace. `create_buf` also sets `b:minicursorword_disable`.
- **A pane's "nothing here" message is cut like a row** (`paint_empty`, with `…`): Neovim clips a line at the window edge silently, so an uncut message reads as a sentence that simply stops.
- **A row's text floors at 1 cell in every pane**, so a narrow pane never pushes the age, counts or status mark past the window edge.
- **A path too long for its pane is cut from the inside** (`render.shorten_path`), never the tail: `first/…/parent/name` → `first/…/name` → `…/name` → `name` → the name cut with its **extension kept**. The first folder outranks the parent because it is the coarser answer (`lua/…/init.lua` vs `tests/…/init.lua`).
- Rows are ordered by `summary.last_ts` — **the newest `"timestamp"` anywhere in the transcript**, matched out of the raw line rather than decoded, from any entry type. Dating from tool results alone leaves a Bash-only conversation at epoch 0; the file's mtime is worse (the CLI appends untimestamped `last-prompt` bookkeeping days later).
- **The order is then frozen** (`model.apply_order`): every criterion moves on its own, so with several agents running a live sort would shuffle the list continuously. `state.order` records the ids in shown order, rows keep their places, and a new session is **sorted in once** at the position the active criterion gives it and then pinned (appending would file every new agent at the bottom of a recency sort). `state.order` is rebuilt from the rows present, so deletions need no cleanup.
- Only two things re-sort: `r` (explicit re-read) and `gs` (`keymaps.sort`) → `agents/sort_menu.lua`, a single-key float (`snacks.win`, else `nvim_open_win`, our own rendered buffer either way) offering `recent`/`name`/`changes`/`status` from `model.SORTS`, with re-picking the active one meaning **reverse**. It is the only place the order is stated, so it names the direction in the criterion's own words ("newest first", "A → Z"), and it answers exactly once however many buffer-local keys are pressed after it closes. The choice lives on `state` and dies with `detach`; the next open starts from `agents.sessions.sort` (old values `added`/`title` are aliases for `changes`/`name`).

**How far back the list reaches**

- `agents.sessions.limit` is **either a count or a span**: `"2w"` (the default), `"3d"`, `"1m"` — thirty days, since a calendar month would make one setting mean different spans — `"all"`, or a plain number for the newest N. `model.parse_limit` reads both and falls back to the default rather than erroring, because it runs on a timer; `config.validate` is where a wrong value is reported.
- `agents.sessions.max` (200) is a ceiling that **holds however wide the window is**, so `"all"` costs a bounded number of rows and folds. A count below it wins; it is never lifted.
- Age comes from the file's **mtime**, not `summary.last_ts`: the enumeration is stat-only, and asking for `last_ts` would mean folding every transcript in the project to decide which ones to show. A row that disappeared once it folded would be worse than one that is a bookkeeping write too young. (This is the one place mtime is the right clock — it answers "was this touched recently", not "when did the conversation last say something", which is what the _order_ needs.)
- **The window never drops what the user is holding on to**: a running agent (`registry.live_ids`), the selected row, and anything pinned. Otherwise a live terminal older than the window would be re-listed by the `live_ids` pass as a synthetic `New session` row, losing its title and counts.
- `state.hidden` counts what was left out, so the centre can say "nothing from the last 2 weeks — 7 older conversations" instead of "no conversations in this project" (`show_empty_notice`). That screen names `gs` and binds it, since `gs` is otherwise bound in the sessions pane alone and the centre is where the message is read.
- The `gs` float has a second section (`model.WINDOWS`, keys `1`/`3`/`w`/`W`/`m`/`a`) for the same reason it states the order: the rows the window leaves out leave no trace of themselves. `on_pick` is answered with `(key, kind)`, `kind` being `"sort"` or `"window"`. With a **count** in force no span is marked — the heading says "newest 30" instead, since marking a row would misreport the list.
- Like the sort criterion, a window chosen with `gs` lives on `state` and dies with `detach`.
- `model.pin`/`model.unpin` keep a conversation listed whatever the window says, and list one the project's enumeration cannot see at all (a search hit from another project, built from the transcript path and cwd the search knew). Pins die with the view.

**Deleting conversations**

- `dd` (`keymaps.delete`) → `transcript.delete` removes the `.jsonl` **and** the sidecar directory of tool results (`<dir>/<id>/`). The row disappears because `refresh_list` re-enumerates, not because anything removed it locally.
- **Deleting the selected (or offered) session moves the selection** (`follow_deletion`) to the row that took its place — the one the cursor lands on, or the one above when the last row went — through `preview_session`, so a running agent is shown and a stopped one offered. Otherwise the centre would keep offering the deleted id, and `i` on that offer would find no row and claim the deleted id with `--session-id`, starting a new conversation under it. The row order is read before the delete. An offer for any deleted id is cleared; nothing left falls to `sync_empty_notice`.
- Irreversible (the transcript _is_ the conversation), so it asks first through `agents/confirm.lua`: a centred `snacks.win` float, else `vim.fn.confirm`. Every path answers exactly once; closing the window counts as "no" (the callback is guarded and deferred out of the closing keymap).
- Takes a **count** and a **visual range** (`3dd`, or `d` over a selection — `_visual_lhs` binds a doubled key under its single form, since over a selection the range _is_ the selection). A batch asks **once**: the dialog names the first `DELETE_LIST_MAX` rows and counts the rest, and `model.delete_sessions` re-enumerates once for the whole batch.
- A session whose agent is still running is refused (the CLI has the file open). Inside a range it is _set aside_ rather than vetoing the gesture; the dialog reports how many were left alone. Only a range with nothing deletable merely warns.
- Stop is `x`, not a `d` key: `map` binds with `nowait`, so a `d` binding would make `dd` unreachable.

**Rewinds (`/rewind`, Esc Esc)**

- **A rewind writes nothing** (2.1.276): "Restore code and conversation" puts the file back and the transcript does not grow by a byte. The retracted lines stay in the file for ever; the only trace is the **next prompt's `parentUuid`**, which names the entry the retracted prompt had named (the selector says "restore to the point before you sent this message", and that is literally what happens). The file restore is done from `~/.claude/file-history/<session>/` backups and leaves no record either, so "conversation only" and "code too" are indistinguishable in the log.
- A linear fold would therefore count every rewound edit as the session's, list files the session no longer touched, draw the retracted calls in Activity, and feed `patch.reconstruct` hunks that no longer apply to the restored file — the chain breaks at the first anchor after the rewind.
- **Recognition** (`note_prompt`): every user message that is not a tool result is noted with its parent (`sum.prompts`); a message whose parent an earlier, still-standing message already has is a rewind to before that earlier one. The two can be as close as 3 lines and a few seconds apart (an Esc Esc before Claude answered). **Do not walk the chain from the leaf instead**: parallel tool calls make the `parentUuid` tree branch (a result is parented to its own call while the next call is parented to the same one), and a leaf walk drops real result entries, edits included.
- The stretch from the retracted prompt's line to the line before the continuing one is recorded (`sum.rewinds`, by **line number**, which is why `_fold_line` counts lines before anything can return) and the fold **starts over** (`refold` → `restart_summary`, in place, since `cache[path]` and `M.events(path)` hand the same table out): what it had counted included those lines. Rare, and bounded by the file like a compaction restart. A rewind that reaches back past an earlier one absorbs it, so each line is inside one stretch. The warm cache needs nothing: it is `partial` and refolds from scratch anyway.
- Skipped lines are still looked at for two things (`fold_rewound`): every `toolu_…` id in a `tool_use` line goes to `sum.rewound_tools`, so `subagents.scan` leaves out a run one of them started, and its children with it (the files are still on disk — the CLI deletes nothing); and the count of them is what the Activity rule says was taken back.
- `file_history` reads the summary first and skips the same stretches, so the reconstruction never sees a hunk the CLI already reverted. `search` deliberately still finds rewound text: the user did say it.
- **The rule** (`render.rewind_line`, a `kind = "rewind"` event pushed where the retracted calls were): `── rewound 14:34 · 12 calls taken back · "the prompt…" ──`, in `ClaudeCodeAgentsRewind` (→ `DiagnosticWarn`: the one row recording the user undoing work). Shown under every Activity filter (`model.feed`/`count_shown`), since whatever the pane lists, the rows above it are after the rewind. Its payload has no `path`, so `<CR>` and `<C-n>`/`<C-p>` skip it like a checkpoint's.

**Checkpoints (`gc` / `gC`, `:ClaudeCodeAgentsCheckpoint[!]`, `agents/checkpoints.lua`)**

- A checkpoint is an epoch second stamped on a **conversation id**, stacked (N checkpoints = N+1 eras) and persisted at `stdpath("cache")/claudecode/agents-checkpoints.json`, because "reviewed up to here" is a fact about the conversation, not the view. `model.delete_sessions` calls `checkpoints.forget`. The store is read once, lazily, and written on every change.
- Everything is sorted into eras by **its own transcript timestamp** (`checkpoints.era`: `ts <= mark` is at or before it, so the era of the checkpoint itself is the older one). The CLI writes whole seconds, so an edit landing in the checkpoint's own second reads as before it — the honest side, since the checkpoint was taken while it was on screen. `add` refuses a second checkpoint in the same second.
- **Changes** needs per-era counts, so `touch_file` keeps `files[path].edits` (`{ts, added, removed, kind}` per non-read result; reads are most of a session's touches and count for nothing) — mirrored to the warm cache, hence `CACHE_VERSION = 3`. `model.changes` buckets a file's edits per era and lists it once per era it was edited in, each row carrying `era = { index, count, from, to, note }` and a payload key of `path\0index` so the cursor holds on the right one; a `kind = "checkpoint"` entry is the rule between eras. Eras run **newest first** like Activity — the current era on top, the rule that opened it beneath — so a file edited after the checkpoint lands above the rule; within an era rows keep first-touch order. Tasks alone runs oldest-first, since the tree is in start order. A summary with no `edits` (a stub, an older cache) dates its totals by `last_ts` rather than vanishing.
- **Activity** slots the rule in from `model.feed` (`with_dividers`) between the events it falls between; one newer than every event sits at the top ("nothing since"), one older than everything drawn is only emitted when the walk drew the whole filtered history (`count_shown`), since below a pane cut to its height it would sit under rows that are not its neighbours. The rule's table is **kept per (session, checkpoint)** (`state.dividers`) — `stamp_feed` ages rows by table identity, so a fresh table per frame would light the rule on every redraw, while a kept one arrives lit once and settles.
- **Tasks**: `subagents.rows` takes `opts.checkpoints` and emits rules between the **top-level** runs by start time (`rules_before`, plus the rest after the walk); a child started after the checkpoint stays under its parent, since where it hangs is what the pane is for. A running task keeps updating whichever side it is on.
- `<CR>` on an era row → `file_view.open` with `era` → `era_steps` picks the steps with `from < ts <= to` and `open_range(first, last)` shows the file as the last left it against what the first found. `open_step` is `open_range(i, i)`. Both sides come from `patch.reconstruct` when an anchor reaches them, else from today's file with the later steps reverse-applied and then the span's own — the same two answers a step gets. An era that left the file as it found it is said (`whole = true`) rather than opened empty. Title note is the era's own name: `(until 14:32, on disk)`, `(since 14:32, reconstructed)`, `(12:00 – 14:32, …)` (`checkpoints.era_note`; the date is added from the next day on).
- `render.checkpoint_line` draws the rule identically in all three panes, in `ClaudeCodeAgentsCheckpoint` (→ `Comment`); in Activity it goes through `fade.dim_group` like any row. Its payload has no `path`, so `<C-n>`/`<C-p>` stepping and `<CR>` skip it.
- **Names** (`checkpoints.set_name`/`names`, store version 2 — `sessions[id] = { marks, names = { ["<ts>"] = name } }`; a version 1 bare list is still read): `a` (`keymaps.checkpoint_name`) on a rule in Activity/Changes/Tasks, and `i` there too (`focus_terminal` checks `checkpoint_under_cursor` first — both keys mean "type here"), open `agents/input.lua`: a one-line float over a real buffer in the search box's style, `<CR>` answers the text (empty clears the name), `<Esc>`/closing answers nil, exactly once, deferred out of the keymap. The model stamps `name` on every rule row it produces (`divider_for`, `changes`, and the Tasks rows after `subagents.rows`), and the renderer draws `· name` after the clock, cut with `…` so a stub of rule survives at the right edge. Names are dropped with the checkpoint (`drop`) and the conversation (`forget`).

**Flags (`m` / `M`, `:ClaudeCodeAgentsFlag[!] [note]`, `agents/flags.lua`)**

- A flag says "I still have to deal with this", and exists because neither existing state does: `done` dies the moment the row is selected (`model.select` → `mark_read`), and `waiting` lasts only while the CLI has a prompt up.
- Two kinds, told apart by the note. A **bare** flag (`{ at }`) ends at the user's next reply: `flags.settle(id, summary.last_reply_ts)`, called from `apply_summary`, strictly later than `at` because both clocks count whole seconds. A flag **with a note** is ended by nothing but the user. Taking the note off restarts the wait at now, or whatever was said while the note held it would end the flag with the note.
- **What a reply is** (`sum.last_reply_ts`; 2.1.25x–2.1.29x): any non-result line carrying an unescaped `"origin":{"kind":"human"}`. That covers `user` entries (typed prompts, slash commands, image-led prompts) **and `queued_command` attachments** — a prompt typed while Claude is working is written only as that attachment, never as a `user` entry. Nothing the harness writes in the user's name carries it: task notifications say `"kind":"task-notification"`; interrupt markers, skill instructions, local-command echoes and subagent hand-backs have no human `origin`.
- Three tool results are replies too, recognised by how `toolUseResult` begins (`REPLY_RESULTS`: a comparison at a known offset, no scan, no decode): `{"questions":[` with `"answers":` (an answered AskUserQuestion), `{"plan":"` (an approved ExitPlanMode), and the rejection text followed by `the user said:` (a call turned down **with words**, which is how a plan is answered with a correction). A bare rejection is not a reply — the conversation is still waiting. The whole opening is compared, not the phrase, since a result can merely quote it. Approving a permission prompt leaves no record and is not a reply.
- `_fold_line` finds `"toolUseResult"` **once per line** (`result_at`) and shares the answer between its tests, which pays for the human-origin scan.
- **The store's I/O is libuv-only, and that is load-bearing** (`flags._io`). `settle` runs inside the fold's `uv.fs_read` callback — a fast context, where every `vim.fn` call (`readfile`/`writefile` included) raises `E5560`, and the fold's `pcall` would swallow the error. The specs' fake filesystem has no fast context, so only a real Neovim shows it. `read_store` replaces memory only once the read has answered, and a file that exists but cannot be read aborts the change rather than writing an empty store over it. The path is a `vim.fn.stdpath` answer too: `flags.path` resolves it on first use and keeps it (the first use is `refresh_list`, on the main loop), and a fast context asking first is told there is no store rather than left to raise. Not resolved at module load — a `vim.fn` call at `require` time makes `agents_view` unloadable under any vim without `stdpath`. One spec drives the module's own `_io` over a fake libuv with `vim.fn` raising.
- **Read again before every change, and whenever the file moves** (`mutate`; `flags.refresh` from `refresh_list`, one stat per pass). One file holds every project's flags and a second Neovim on another project is the ordinary case: writing back a copy read at startup would drop what the other one flagged since. Writes go through a per-process temporary file and a rename. (The checkpoint store does neither.)
- `refresh_list` keeps every flagged id listed whatever the window says, like a running, selected or pinned one. It also re-folds a row whose flag is `pending` and whose cached summary no longer matches the size/mtime the enumeration just stat'ed: nothing else re-reads a conversation that is neither selected nor running here, so one answered from another terminal would keep its flag until next selected.
- Drawn as `⚑` (U+2691, not emoji-capable, one cell) between the bullet and the title in `ClaudeCodeAgentsFlagged` (→ `DiagnosticWarn`), the note after the title in `ClaudeCodeAgentsFlagNote` (→ `Comment`). `render.fit_title` shares the room: both whole when they fit, otherwise the note gets what the title leaves free or `NOTE_SHARE` (40%) of the room, whichever is more — generated titles fill the pane, so what they leave free is usually nothing. The winbar counts the flagged rows (`Sessions · ⚑ 2`) and is written only when it changes; the centre's offer screen shows the note in full.
- `m`/`M` act on the **row under the cursor** like `x` and `dd`; the command acts on the **selected** session, since it is typed from the agent's terminal. `M` opens `agents/input.lua` on the current note, which is also how a note the row cut is read. Flagging never re-sorts (the order is frozen); the `status` criterion ranks flagged rows above every unflagged one (`FLAG_RANK`).
- Kept at `stdpath("cache")/claudecode/agents-flags.json`, beside the checkpoints. `model.delete_sessions` calls `flags.clear`.

**Numbered follow-ups (`A`, `:ClaudeCodeAgentFollowUp`)**

- `keymaps.follow_up` → `agents_view.new_follow_up(session_id)`: a new agent called what a session is called, numbered on (`plan` → `plan-2` → `plan-3`), selected and focused exactly like `a`'s (both go through `start_agent`). For work that outgrows its conversation: nothing of the old context comes along, only the name. In the sessions pane it means the row under the cursor, like `x` and `dd`; in every other pane, on the centre's notice screens and from the command it means the selected session. It starts in `row.cwd` — where the session it follows is resumed from — falling back to the view's directory when that one is gone.
- **The name rides the launch**: `registry.launch` takes `name` and appends `--name=<quoted>`. `--name` beside `--session-id` writes the same `custom-title` + `agent-name` pair `/rename` writes, and writes it **with the first message** — a named launch left idle has no transcript, only the name in its prompt box (2.1.295). So nothing is typed into the terminal on the user's behalf, and the fold needs nothing new (`sum.name`).
- Until that first message the row is the synthetic one, titled from the registry's `term.name` (what the launch's conversation is called, as far as the launch knows) instead of `New session`; `refresh_list` carries the title over when the enumeration takes the row, so it never reads anything else.
- `--name=<value>` as **one word**: a name may begin with a dash and would be read as an option (`--name=-lead it's-2` is accepted), and `parse_command` expands a word-initial `~`. Quoted with `utils.shell_quote`, the inverse of `shell_split` — the launch string is split by us and spawned without a shell on every platform, so `vim.fn.shellescape`, which follows `'shell'`, quotes for a program that never runs. Never passed with `--resume`: that conversation is called what its transcript says.
- `model._next_name`: the name is the row's **title** (rename → generated title → first prompt, the name the session is read by), on one line. A trailing `-N` of up to `COUNTER_DIGITS` (3) digits is the counter and keeps its width (`part-09` → `part-10`); a longer run is a date or a ticket (`notes-20261009` → `notes-20261009-2`), which also keeps `%d` away from a number a double cannot hold. Titles already in the list are stepped over — a live synthetic row included, so asking twice from `plan` gives `plan-2`, then `plan-3`. Only listed rows are asked: a name is a label, not a key, and avoiding a duplicate is not worth folding every transcript in the project.
- A session still titled with our own placeholder has no name (`model.follow_up_name` → nil): the key says so and starts nothing. The centre's offer screen names the key together with what the new agent would be called, and leaves the line out for such a session.
- **The CLI carries a name through `/clear`** (2.1.295, for a `--name` and for a `/rename` made since), and for a named conversation it writes the new transcript **at once** — the name pair is its first lines — where an unnamed one's is written with the first message, or as the CLI exits. So a cleared named agent is enumerated straight away, as a file with no fold and no row before it, which would read as the id prefix until the fold lands — on the row the user is looking at.
- **So the launch is told the name** (`registry.set_name`, from `note_session_switch`): `term.name` starts as what `--name` said and, on a switch the CLI reports as `SessionStart(source="clear")` (`switch_opts.cleared`; the field is present on 2.1.295), becomes what the conversation being left was called — `model.given_name`, the transcript's `sum.name`, never the generated title, which is not taken along. `known = false` (nothing of that transcript read: a launch cleared before its first message) keeps the launch's own name. Any other switch — `/resume` from inside the CLI, a fork — is onto a conversation with a name of its own or none, so the name is forgotten rather than left to describe the wrong chat. `model`'s `launch_name` is the last fallback of a row's title, after the fold and after the title the row had (`refresh_list`'s enumerated rows, and `row_at` for one found elsewhere in the store), so it only ever shows for a transcript nothing has read; without that fallback it would never show at all.

**Row actions**

- **A row in either pane is a record of work, not a file reference.** `<CR>` shows what the session did to that file (`agents/file_view.lua`): today's content with the session's changes rendered inline by unified.nvim; for a read row, the lines that read covered, in live-cursor's own highlight group.
- **An Activity edit row is one call, and opens as that one edit** (`prefer = "step"` with the row's `tool_id`; a subagent transcript's call lines do the same). `file_history` keeps `steps` beside the flat `hunks` — one per result, oldest first, with the call's id, kind (`edit`, or `write` when the result carries `content`) and its own hunk tables. `open_step` takes both sides from `patch.reconstruct` (`states[i-1]` vs `states[i]`, memoised on the history as `reconstruction`) and titles it `reconstructed`. Without an anchor reaching that step it rebuilds the moment from today's file — every later step reverse-applied, then the step's own hunks for the other side — titled `on disk`; any hunk that fails to locate there means an outside edit has touched those lines, so the call's patch is shown as diff text with `file moved on` in the title — never an approximate inline diff. Title says `(edit 3 of 7, …)`, the position among the session's edits to that file, so `<C-n>`/`<C-p>` read as a sequence. A `tool_id` the history has no step for (a result naming no call) falls back to the cumulative diff. Changes rows carry no `tool_id` and stay cumulative.
- **The diff is rebuilt from the record, not from disk, whenever the record allows** (`patch.reconstruct`): the transcript holds the whole file at certain moments — an `Edit`'s `originalFile` (a string only up to ~10KB; `vim.NIL` otherwise), a `Write`'s `content`, and a whole-file `Read` (`startLine == 1`, `numLines == totalLines`, not `truncatedByTokenCap`; its `content` is the raw file) — and every hunk was cut from the file exactly as it stood before its call. So from any anchor the other states follow: forward with `patch.forward_apply` (old side located nearest `oldStart`, hunks of one call applied bottom-up, added lines from `hunk.exact_new` ← `newString`), backward with `reverse_apply`. An outside edit between steps breaks the chain (a hunk that fails to apply whole stops it); a later anchor corrects it, otherwise the states past the break are unknown. `fold_history` records `step.before` (`originalFile` → `""` for a creation → a whole read since the previous step, consumed by the step) and `hist.read_anchor` (a whole read after the last step, the end state). The float's title says `reconstructed`: it is the file as it stood then, and what happened to it since does not change the view. A session that edited and reverted is reported, not opened.
- **Only without an anchor** (typically a large file read in windows) is the old path taken — reverse-applying the session's hunks to the file on disk, newest first, each located by content nearest its recorded line — and the title says `on disk`, plus how much of the session's work is still present (`(on disk, 3/5 changes still present)`) when hunks were overwritten since. When nothing can be located, the file is gone, or unified.nvim is absent, the hunks themselves are shown as diff text — the CLI's own record, which cannot be stale.
- **A hunk is not the file's text: the CLI writes every tab in `structuredPatch` as two spaces** (and a hunk may carry a `\ No newline at end of file` line). `oldString`, `newString` and `originalFile` keep the tab. Matched verbatim, no hunk touching a tab-indented line would locate, and each skip takes its older neighbours down too. So `patch.reverse_apply` locates against `patch.shown` (tabs → two spaces, trailing CR dropped) and rebuilds with the file's own text: context lines from the file, removed lines from `hunk.exact_old` (`patch.annotate`, called in `fold_history`: `originalFile` by position, else `oldString` by shown text), else re-tabbed leading indentation when the located block is tab-indented. `originalFile` is dropped above ~10KB, which is why `oldString` matters: it recovers removed lines exactly without `originalFile`. `\` lines belong to neither side.
- The baseline handed to unified.nvim ends in a newline: `show_against_text` appends one to the buffer's text when `'endofline'` is set, so a baseline without it marks every file's last line changed.
- `.` (`keymaps.git_diff`) → `file_view.open_against_head`: same float and renderer, the file's committed content as the baseline (`git.file_at_head`). `git._working_copy` walks up for the nearest `.git` (dir or file) or `.svn`, with a stat per candidate so a deleted directory is walked past. Git: `git show HEAD:./<name>` with `-C <the file's own directory>` so the repo root never has to be found, run from the root found (which exists even if the file's directory was deleted). svn: `svn cat -r BASE <path>@` — `BASE` is what `svn diff` compares against, the trailing `@` stops an `@` in the name reading as a peg revision — and the float says `BASE` wherever it would say `HEAD`. Non-zero exit inside a working copy = never committed, so every line is an addition; outside one git is still asked (a `GIT_DIR` repository has no marker) and failure means **not versioned**, which is said instead of opening an all-additions diff; a command that could not start (`text == nil`, including a `jobstart` id ≤ 0) is said too. A file identical to its baseline says so instead of opening an empty diff; without unified.nvim it falls back to `vim.diff` text. This read bypasses `git.run`, which drops empty lines (right for status, wrong for file content). Status letters in the Changes pane are git-only; in svn they fall back to the transcript's own.
- `gf` (`keymaps.goto_file`) opens **the file itself, on disk, in a new tab** — the other two are for reading what happened, this one is for working. A new tab carries none of the agents tab's vars. A path that is no longer readable is refused with a log line (`tabnew` on a missing path opens a buffer whose first `:w` resurrects the file). The tab open itself is `file_view.open_in_tab`, shared with the edit keys below.
- **A key that edits, in a `file_view` float, edits the file** (`bind_edit_keys`, on every scratch buffer `file_view` builds — inline diff, read view, patch text, HEAD text diff; never `float.open_file`'s real buffer). `M.EDIT_KEYS` per mode (`n`, `x`): the float closes, `open_in_tab` opens the file, and the key is fed back with `M._key_prefix` (register unless it is the one a plain key uses under `'clipboard'`, then `v:count`). Works on 0.12.5 for `dd`, `3dd`, `ciw`, `o`, `"ap`, `gUiw`, `>>`, `Vjd`, charwise and block visual.
  - **Operators are bound alone, `nowait`, and the key is replayed** rather than dropped: whatever follows (`d`, `iw`, a surround plugin's `s"`) is still in typeahead and must complete in the file. Dropped, `dd`'s second `d` would land in the new tab as a pending operator; bound as `dd`, `d` would wait on the timeout.
  - Both feeds are `i` (front of typeahead) — appended, a fast `ciw` would reach the file as `iwc`. The key is remapped (`m`, so a plugin's `ds` completes), the visual reselection (`<mode><Cmd>call cursor()<CR>`, fed second so it runs first) is not. Visual is left with `:normal! <Esc>`, which saves and restores typeahead; `nvim_feedkeys(…, "x")` would execute what the user typed next in the float.
  - Position: `_disk_position` maps a `"file"` float (a version of the file) through `vim.diff` indices against the lines being edited (`_map_line`; a changed line lands on its counterpart), and a `"patch"` float through its `@@` header to the new-side line (`_patch_line`), then by text nearest there (`patch.shown`, since the CLI writes tabs as two spaces). The lines being edited are a loaded buffer's when there is one (unsaved changes), else disk.
  - A key with a mapping (`maparg`, read inside `nvim_buf_call` so a pane's buffer-local `x` does not count) or equal to the leader is left alone — flash/leap `s`. `ALWAYS_TAKEN` (`gc`, `[<Space>`, `]<Space>`) is an edit under every mapping. Not `u`/`<C-r>`/`.` (nothing to undo; `.` would repeat a change made elsewhere) and not `gr` (Neovim's LSP prefix).
  - A file no longer on disk: no action, float stays.
- **The float's title says where the file is** (`file_view.title` → `utils.path_title`, see 13), not just its tail: a session touches several `init.lua`, and a row is a record of work rather than a file you already have open. Relative to the directory the conversation ran in (`cwd`, passed from `model.selected_cwd`), with the note (`(read)`, `(vs HEAD)`, `(3/9 changes still present)`) after it.
- File history is read on demand (`transcript.file_history`, prefiltered on the basename) rather than folded into the summary, and answers through `vim.schedule` — its reads land in a libuv fast context where opening a window is `E5560`.
- The Changes pane takes `+N/-N` from the transcript and only its `M`/`A`/`D`/`?` letter from git (`agents/git.lua`, pathspec-restricted, single-flight, newline-delimited rather than `-z` because `jobstart` renders NUL as `\n`), so the pane and the session row cannot contradict each other.
- **A file no longer on disk is drawn `D` and dimmed whole** (`ClaudeCodeAgentsDeleted` → `Comment`), counts kept but without blocks or flashes. Deletion is git's `D` **or** our own `uv.fs_stat` answering `ENOENT` (`model._is_gone`, run in `refresh_git` even with `git = false`): a file the session created and then `rm`'d was never tracked, so git says nothing and the transcript still calls it an add. `refresh_git` also runs when the selected transcript's `last_ts` moves (a shell `rm` is not a `WRITING_TOOLS` call, and polling reports no tool), and a request inside the rate gate schedules one trailing refresh instead of being dropped. `.` on a deleted tracked file shows HEAD as all removals, always as diff text (a buffer on the missing path is one `:w` from resurrecting it).
- **A file in the CLI's scratchpad is drawn like a settled tool call's label** in Activity — `fade.dim_group(hl("title"), nil)`, the very group a rested Bash description gets, so the two follow each other through `fade = false`, `highlights.title` and colorscheme changes. Quieter than a path, not grey (grey means deleted); counts keep their blocks, and a deleted one is grey like any other. `transcript.is_scratchpad` matches the **shape** `…/claude-<uid>/<slug>/<uuid>/scratchpad/<file>`, either separator, rather than deriving the directory (2.1.274 builds it from `<temp root>/claude-<uid>/<slug>/<session>/scratchpad`): the root is `/private/tmp` on macOS, `/tmp` on Linux, `$CLAUDE_CODE_TMPDIR` when set. **Windows has no uid: the directory is a bare `claude`** under `os.tmpdir()` (`%TEMP%\claude\D--Git-proj\<uuid>\scratchpad\…`, read from the win32-x64 2.1.280 build), so the pattern takes `claude` with an optional `-<digits>`. Not tied to the transcript's own id — resumed and forked sessions write to another session's scratchpad. The UUID segment keeps out a project folder that is merely called `scratchpad`.

**Navigation**

- `<C-n>`/`<C-p>` (`keymaps.next_session`/`prev_session`) move the selection from **any** pane and from inside the terminal, in terminal mode as well as normal.
- **Neovim reads the key after a terminal's `<C-\>` through mappings**, so a terminal-mode `<C-n>` alone takes the `<C-n>` of `<C-\><C-n>` and the user cannot leave the agent's terminal. `map_cycle` therefore also maps `<C-\>` + each cycle key to itself in terminal mode, non-recursively: the longer mapping wins and its replay is not remapped.
- `next_pane` (`<Tab>`) is bound on an agent's terminal buffer in normal mode as well (`bind_terminal_keys`), as the help's "anywhere in the view" says; terminal mode's Tab stays Claude's.
- A live conversation is swapped into the centre at once. A **stopped one is selected but never started** — cycling is how you read what sessions did, and every pane follows the selection. The centre shows a notice naming the conversation and the key that starts it (`show_start_prompt`, recorded as `state.pending_start`); the notice is one reused scratch buffer (`state.notice_buf`), which is also what a dead agent's pane shows.
- `focus_terminal` (`keymaps.focus_term`, `i`) resumes a stopped conversation and then lands in it — "put me in this session" is one intent either way. It falls back to the offer if pressed before the list arrives, and starts a new agent when there is neither an offer nor a session.
- **The view opens already pointed at a session** (`offer_initial_session`, armed by `state.await_initial`, fired from the model's change callback as well as `open`, since the list folds asynchronously). Otherwise the centre holds `tabnew`'s blank _modifiable_ buffer where `i` edits a scratch file. It offers the selected or newest session, starts nothing, and stands down once a terminal or earlier offer owns the pane. `refresh_start_prompt` repaints it when the fold replaces the placeholder title.
- A conversation running in another tab is offered as a **jump**, not a start (two CLIs on one transcript).
- **A project Claude has never run in gets its own screen** (`show_empty_notice`, painted by `sync_empty_notice`): the offer bails on an empty list and waits for a model change that never comes. Enumeration is synchronous (`transcript.list` is stat-only), so `open` answers immediately: no conversations yet, plus the key that starts one. That key (`keymaps.new`, `a`) is bound on **every** centre notice screen (empty project, offer to resume, ended agent) and named in each one's hints — whatever the centre offers, no agent is running there. It is bound in `apply_notice_keys` (not only via `KEY_SPECS`) so it holds under a bare config. The same screen returns when a project _becomes_ empty and re-arms `state.await_initial`.
- **Inside a file float those keys step through the pane's rows** (`bind_float_nav`): the float is a view of one row, so they walk the rows one level down, wrapping at both ends, skipping rows with no file, moving the pane's cursor along and keeping the baseline the float was opened with.
- Stepping **swaps the float's content in place** (`float.create`'s `reuse`, threaded through `file_view`) rather than close-then-open: `file_view.open` reads history asynchronously, so a close-then-open leaves focus in the _pane_, where the same keys change the session. Reuse also stops the cascade walking down the screen per file.
- Repeats are **coalesced**: the aim moves on the keypress and only one open is in flight, so holding the key walks at key-repeat speed and opens the row it settles on.
- Bound only on scratch buffers we made — `float.open_file` shows the real file buffer, where a buffer-local `<C-n>` would follow that file into the editor.
- **Every pane's cursor is held on its row, not its line.** A repaint replaces the lines wholesale and Neovim keeps the cursor's line number, so a row landing above it would slide another under the cursor (a new Activity event, a Changes file first read then edited, a Tasks shell started inside a subagent). `render` gives every payload a `key` (session id; `transcript.event_key` for Activity — the call's `toolu_…` id, which file events carry too, read from the result's `tool_result` block; path; `kind\0id` for Tasks), and `redraw` reads the key under each cursor before painting and puts the cursor back on it after (`cursor_row`/`restore_cursor_row`; ties go to the nearest line).
- **Activity's top row watches the newest**: a cursor on line 1 stays on line 1 as events land, since holding it would scroll the newest rows out of sight a screenful later. Any other row is held, and so is a top row a float is showing; `gg` returns to watching.
- A held Activity row is drawn however far it is pushed: `model.feed(visible, keep)` walks past the pane height until every kept key is drawn, never past `feed_limit`, and the pane scrolls to keep the cursor on screen. A float row the pane no longer draws (the filter hid it) is let go of (`drop_lost_float_rows`), or the feed would walk the whole history every frame looking for it.
- Held only **within one session**: after a selection change the rows are another conversation's (the same path in Changes included), so the cursor stays on its line (`state.rows_session`).
- **The float's stepping state names rows too**: `float_nav` carries `key`/`aim_key` beside `lnum`/`aim`, which are only where the rows were last seen. `step_float` steps from where the aimed row is _now_, and `open_aimed` resolves the aim by key when the open lands.

**Search (`agents/search.lua`, `gf` in the sessions pane / `keymaps.search`)**

Same key as `goto_file`, different meaning; possible because no pane is offered both.

- Searches **what was said** (`user`/`assistant` `text` blocks), the **paths touched** (`toolUseResult.filePath`), **what the turn ran** (`tool_use` block inputs), **what it was reasoning about** (`thinking` blocks), and the title.
- Deliberately **not** tool output: a word in a file's contents would match every session that ever read the file (mostly `attachment` entries and tool results).
- A `tool_use` input skips path fields (`file_path` and friends), since the call's `toolUseResult` already reports that path as a `file` match. Remaining string fields are read in `TOOL_FIELDS` order then alphabetically (`pairs` order is not stable, and a result list that reorders itself between identical queries is worse than a dull order).
- **Match priority is decided over the whole file** (`SEARCH_KINDS`: said → file → ran → thought), not within an entry — per-entry ranking lets reasoning take every row. The scan collects into a **bag keyed by kind**, stopping when the top tiers are full (`bag_done`) or at `limit * 3` of anything.
- Matching is **literal and smartcase** (`transcript.compile_query`); case-insensitivity is compiled into a Lua pattern (`[aA]`) rather than lowering the haystack.
- **There is no index.** Each query past the debounce re-reads the store and is cancelled by the next keystroke. Affordable because the prefilter runs on the **raw JSON line** (non-matching lines are never decoded) and a scan stops at `max_per_session` (3). A query matching nothing sweeps ~90MB of transcripts in under a second, with results streaming as each file finishes.
- Cost of raw-line prefiltering: a query containing a quote, backslash or newline is spelled differently in the file and will not be found. Ordinary words, paths and identifiers are fine.
- A line over `SEARCH_LINE_LIMIT` (256KB) is skipped rather than decoded, and walked a slice at a time.
- Scans run four at a time but results are stored **by session position**, so the list is in the sessions pane's order however reads finish. The cursor is anchored to its session across repaints.
- **Two windows**: the query is a real buffer (every editing key works), the list is `focusable = false` and never entered. `<C-n>`/`<C-j>`/`<Down>` and `<C-p>`/`<C-k>`/`<Up>` drive its cursor from the input; leaving the input cancels.
- Moving **previews** (`agents_view.preview_session` — `cycle_session`'s body reached from an id; panes follow, nothing starts), so `<Esc>` restores the selection the picker opened with.
- `<CR>` is `focus_terminal`'s intent (`agents_view.enter_session`): select, resume if stopped, land in it. The query outlives the picker and dies with the view.
- **The scan is not bounded by the list** (`M.SCOPES`, `<Tab>`/`<S-Tab>`): `visible` reads the pane's rows, `project` every transcript for this cwd (`transcript.list`), `disk` every project directory (`transcript.list_all`). It opens on `project` — the conversation being searched for is very often the one the window dropped, which is why you are searching — and the scope is remembered like the query, dying with the view (`search.reset`).
- Order follows the same rule as the list: **the pane's rows first, in the pane's own order**, then everything else by mtime. `sessions_for` dedupes by id, so a conversation the project pass already listed is not listed again by the store-wide one.
- A `disk` hit is resumed **in the directory it ran in**, read from the transcript by `transcript.cwd_of` (memoised, one bounded synchronous read) — the slug is not reversible. The row is labelled with that directory's tail, read only for rows that actually match.
- A hit with no row is **pinned** (`model.pin`) before the panes are pointed at it: every pane follows a row, and `select` reads the launch directory from one. Pins made while merely browsing are taken back when the picker is cancelled.
- No cap on a `disk` scan — it streams — but the paint is throttled (`REDRAW_MS`, 60ms; the last one is immediate) since a repaint is the whole list, and only `MAX_LISTED` (60) sessions are drawn, with a line saying how many more matched.

**Tasks pane (`agents/subagents.lua`)**

- Under Changes, split at `layout.sessions_height` so its divider lines up with Sessions/Activity; `state.sizes.changes` is snapshotted and restored like the other sizes. Draws the selected session's subagents **and background shells** as one tree: connectors, state glyph (`●` running, `✓` done, `✗` failed, `⊘` stopped), name, tokens, runtime. Internally the `subagents` pane (keys, `state.wins`, config); only the winbar and help say `Tasks` — the CLI's own word for both kinds.
- The name column shows each run's `description` by default (several `general-purpose` rows are told apart only by it); `g.` (`keymaps.subagent_label`) toggles to the agent type, or a shell's command (`model.subagent_label`, lives on the view and dies with `detach`, like the Activity filter). The winbar marks only the non-default reading (`Tasks` / `Tasks · type/command`) instead of a notify. A description is collapsed to one line and falls back to the type when empty. The name's room floors at **1 cell**, not a readable minimum, so it is always cut with `…` rather than pushing the numbers past the window edge, where Neovim clips silently.
- **The store layout** (2.1.270): each subagent has `<session>/subagents/agent-<id>.jsonl` plus `agent-<id>.meta.json` (`agentType`, `description`, `toolUseId`, `parentAgentId`, `spawnDepth`, `requestShape`, and `worktreePath` for a run spawned with `isolation: "worktree"` — drawn `⎇`, see Worktrees). Nested subagents live in the **same flat directory**; `parentAgentId` makes the tree. A parent whose descriptor is unreadable puts its children at the top rather than dropping them.
- **A run is dated by its transcript's first line** (`started_at` → `sum.first_at`, the fold's `first_ts` with its fraction), never by the descriptor: the CLI rewrites the descriptor later (2.1.299: e.g. when a background run first waits on a shell of its own; for some runs minutes to hours after it started), and birth time moves with it. The fraction keeps runs launched from one message, milliseconds apart, in launch order. The descriptor mtime is only the fallback while the transcript is unfolded.
- **How a run ends is recorded by its launcher, not by the subagent**: a background run gets a `<task-notification>` (`<status>`, `<subagent_tokens>`, `<duration_ms>`) in the launching transcript, written twice (a `queue-operation` enqueue, then the delivered `user` entry) — and for a nested run the enqueue also lands in the session's transcript. A foreground run gets the `Agent` call's `toolUseResult` with `totalTokens`/`totalDurationMs`. `transcript._fold_line` folds both into every summary (`task_notes` by agent id, `agent_results` by tool_use id), so `subagents.rows` merges the session's summary with every subagent's.
- `_task_notification` checks structurally, like `_is_interrupt_line`: only a `queue-operation` enqueue or a `user` entry whose whole string content is the notification (optionally after the `[SYSTEM NOTIFICATION` header). A tool result quoting one — reading a transcript does — is skipped before decoding.
- **A notification can be stale**: a resumed agent (sent another message) notifies again later. A note only ends the run when the subagent's newest line is no newer than it (same second counts as ended; the note is written after the last line).
- **A notification can be interim** (2.1.299): a subagent whose turn ends while a shell or subagent of its own still runs is reported `<status>completed</status>` with the summary `Agent "…" is waiting on its own background work` (and a `<note>` saying the same task id notifies again). `_task_notification` marks it `interim`; `classify` ends nothing on it, so the row reads running while the session is live or the run was written within `STALE_S`, and the subagent float draws it as `… waiting on its own background work: <name>`, not `finished:`.
- Live tokens: `_usage_tokens` decodes only the balanced `usage` object of the newest assistant line (input + cache creation + cache read + output ≈ the CLI's `subagent_tokens`). Raw key matching is order-dependent because `usage.iterations` repeats the keys.
- **Running with no recorded end** requires the session to be live (`model.is_live`) or the subagent's transcript/descriptor to be written within `STALE_S` (10 min, the longest a single tool call may run). Otherwise its CLI exited without notifying anyone, and the row reads stopped. A foreground `Agent` call the interrupt marker resolved (`agent_calls[id].status`) is stopped too.
- **`<CR>` opens the run's transcript in a float** (`agents/subagent_view.lua`, routed through `open_row` like tool rows, so `<C-n>`/`<C-p>` stepping works; `next_open_row` counts `kind = "subagent"` rows). A pure core (`fold_line` → document, `render` → Markdown lines, marks, links, folds) is what the specs drive; `filetype = markdown`, so render-markdown/markview draw it.
  - Headline: `# <description>` in full, then `` `type` · state · tokens · runtime ``. The border title carries only type/state/cost (a border cuts at its right edge).
  - Tool **output is never rendered**, only summarised (`summarize_result`: `N lines`, `+A -R`, `N tokens`, `started in the background`, `✗ <first error line>`, `declined`) — it is almost all of a subagent transcript. A result line over 256KB is summarised from its raw text. File tools are named by their path relative to the session's cwd; labels are cut at 100 cells with `…`.
  - Thinking is a closed manual fold per block (`_thinking_` header), every line on `ClaudeCodeAgentsFoldable` (→ `ColorColumn`) so an open block reads as one piece; a closed one keeps Neovim's `Folded`. **`<Tab>` toggles the fold under the cursor** (`za`, nothing off a fold). It is mapped **before** `float.bind_close`, which skips any key the buffer already maps — otherwise its `<Tab>` (focus next float) wins. `l` still opens a fold only because of Neovim's own `'foldopen'` default, which is global and left alone.
  - Messages to the run (the prompt, later messages) are drawn like Claude Code's own: `›` (dimmed) then the text, continuation lines indented, every line on `ClaudeCodeAgentsPrompt` (→ `CursorLine`). No `## Prompt` heading.
  - **`<BS>` walks back up**: `<CR>` on a child passes `history` (the chain of `{ agent_id, lnum }` it came down), the child's header gets ``← `<BS>` back to <parent>``, and `<BS>` reopens the parent in the same float with the cursor on the line that opened the child. Live updates rewrite only from the **first line that changed** — for a running run that is line 2 every tick (its runtime) — and a cursor on the last line follows the end. Folds are therefore **rebuilt every rewrite, never re-applied** (`restore_folds`): each window's open/closed state is read per block ordinal before the rewrite, `zE` clears them, and each is recreated and reopened if it was open. `:fold` over a range that already holds a fold nests a new closed one inside it, so re-applying would stack a level per tick.
  - User entries: the first is the prompt; bracketed/tagged ones are the harness (`> …`); an interrupt is `> ⊘ interrupted`; a `<task-notification>` is a `finished:` line. A call with no result while the run is not running reads `⊘`.
  - A child run's `Agent` call line (matched by the child's `toolUseId`) and its notification line are **links**: buffer-local `<CR>` swaps that child into the same float (`reuse`), and `on_open` rebinds the stepping keys on the new buffer.
  - **Every other tool line is a call** (`render`'s fifth return, `{ tool_id, tool, label, path, read, status }`): `<CR>` → `open_call` opens exactly what the Activity pane opens for that row, reading the **run's own transcript** — `file_view.open` for `tools.FILE_TOOLS` with a path (`prefer = "read"` with the read window from `toolUseResult.file` for a `Read`, else the run's diff), `tool_view.open` otherwise. A new float stacked on top, never `reuse`, so `q` lands back in the transcript.
  - Reads are chunked through `transcript._io`, with an incomplete trailing line carried to the next read. **Folding is scheduled onto the main loop**: the read callback is libuv's fast context, where `vim.fn` (used by `utils.truncate`) raises `E5560`.
  - A 1s follow timer per buffer (stopped on `BufWipeout`) calls `subagents.refresh(session)` before pulling: the headline's state and tokens come from folds the pane keeps current only for the selected session.
- A running subagent keeps `model.poll` marking `dirty.subagents`, so the runtime ticks at `poll_ms` in hooks mode too, without taking the frame clock. `refresh_subagents` folds the session and every subagent transcript (a stat each when unchanged) and repaints only when one grew. Subagent summaries are left out of the warm cache file.

**Background shells (`subagents.rows`, `agents/shell_view.lua`)**

Only background shells and monitors — foreground shells are Activity rows already. Monitors ride the same record (`task_type = "monitor"`, drawn `~`, events where tokens go).

- **The store** (2.1.270): a `Bash`/`PowerShell` `tool_use`, then a result whose `toolUseResult.backgroundTaskId` names the task (`b4mk05121`) and whose text says `Output is being written to: <path>`. The same field marks all three routes — `run_in_background`, Ctrl+B (`backgroundedByUser`), moved there on timeout. A print-mode subagent's result has no `toolUseResult` (see Transcript store), so `background_from_text` reads the id from the result's own text, which must open with one of the four wordings in the 2.1.300 binary (`Command running in background with ID: <id>.`, `…manually backgrounded by user with ID: <id>.`, `…timeout and was moved to the background (ID: <id>).`, `…moved to the background (ID: <id>) so that a message…`), each followed by `Output is being written to:`. Output merely containing the sentence is not a task. The end is a `<task-notification>` with `<tool-use-id>`, `<output-file>`, `<status>` (`completed`/`failed`/`killed`) and the exit code **only in `<summary>`** (`… (exit code 0)`, `… failed with exit code 144`), in the **launching** transcript — a subagent's own for its shells, enqueued in the session's too.
- **Output lives outside the store**: `<realpath($CLAUDE_CODE_TMPDIR or /tmp)>/claude-<uid>/<slug>/<session>/tasks/<id>.output` (the CLI's rule). The path is **read from the result text, never derived** (the temp root is platform- and symlink-dependent); the JSON-escaped separators are undone for Windows. Foreground shells stream to the same directory but their file is deleted on completion; background files persist until swept — a subagent's shell file can be gone later. A missing file never reads as running.
- Folding (`transcript.lua`): `fold_tool_use` records every shell call in `sum.shell_calls` (regardless of `feed_tools` — the tool_use branch decodes Bash/PowerShell lines even with tool rows off). `settle_shell` runs on result lines **raw, never decoded** (a foreground result carries its whole output): it drops the pending call and, when `"backgroundTaskId":"` is present unescaped, promotes it to `sum.shells[task_id]`. An interrupt marker clears `shell_calls`. `_task_notification` also returns `tool_use_id`, `output_file`, `exit_code`.
- `subagents.rows` walks shells as nodes of the same tree (parent = the subagent whose transcript holds the shell), sorted by start with the subagents. `shell_state`: a note decides (non-zero exit → failed); without one, a stat of the output file — gone → stopped; else running if the session is live or the file was written within `STALE_S`. `ended` (a note exists) is what lets a float stop following.
- Pane row: `$ ` after the glyph, tokens field blank. Payload `{ kind = "shell", task_id, tool_id, transcript }`; `next_open_row` counts it.
- **`shell_view`**: header (`# description`, the command under its prompt via `tools.command_lines`, status line, `tools.rule` over the output), then the file tailed on a 500ms timer. `feed` splits on `\n`, keeps what follows a line's last `\r` (progress bars; a trailing CR is a CRLF, not a redraw), carries SGR state across reads (`ansi.parse(lines, state)`), and draws the unfinished last line from a **copy** of that state, replaced when the rest lands. The first read starts `TAIL_BYTES` (1MB) from the end, dropping the partial first line; the buffer keeps `MAX_LINES` (10k). Everything left out, a missing file, or "nothing yet" is said on the rule. Cursor on the last line follows; elsewhere it stays put. Status and title re-derive per tick via `row_for` (the pane's rows, which know liveness) else `subagents.rows`; `subagents.refresh(session)` is called first since the notification lands in a transcript the pane only folds for the selected session. The timer stops one quiet tick after a recorded end (the last write can trail the notification).
- **Monitors** (2.1.270): call `Monitor` with `command` **or** `ws.url`, `description`, `timeout_ms`, `persistent`; result `{taskId, timeoutMs, persistent}` whose text names **no output path** — yet one exists at `tasks/<id>.output` (stdout, stderr prefixed `[stderr] `). `subagents.tasks_dir` takes the directory from any path the session's records state, else the binary's rule (on Windows `<realpath($CLAUDE_CODE_TMPDIR or os.tmpdir())>\claude\…`, with `_win_tmpdir` mirroring Bun's `TEMP` → `TMP` → `<SystemRoot|windir>\temp`, empty variables skipped as JS `||` does). Each event is a `<task-notification>` with `<event>` and **no `<status>`** — `_task_notification` must not default those to `completed`, which would end a monitor on its first event; they fold into `sum.task_events` (counted from the `queue-operation` copy only, since each is written again on delivery). Ends: exit → a status notification (`… script failed (exit 2)` — `exit N`, not `exit code N`; a clean end says `stream ended` with no code, so the footer's code is used); **expiry → only a last event** `[Monitor expired after …]` (older CLIs: `[Monitor timed out …]`).
- **Ends nothing notifies**: a shell or monitor stopped with `TaskStop` gets **no notification** — its only transcript record is the TaskStop result `{message = "Successfully stopped task: …", task_id, task_type = "local_bash"}` (`note_task_stop` → `sum.task_stops`). The CLI also closes every task's output file with `\n[exited with code N]\n` or `\n[killed]\n` (stopped, or expired); `subagents.output_footer` reads the last 128 bytes (`_io.read_tail_sync`, cached by size/mtime) as the backstop. `shell_state` precedence: status notification → TaskStop → expiry event → footer → resume guess → file gone (stopped) → live/recent (running). `how` = `killed`/`expired`/`orphaned`.
- **A resumed CLI guesses**: on resume it writes `<status>stopped</status>` with `Background shell command didn't finish before the previous session ended` for every task it found no end for — including ones whose end _was_ recorded in a form it does not count (a monitor's expiry event). `_task_notification` marks those `orphaned`, and `shell_state`/`workflow_state` rank them below every recorded end; their timestamp is the resume, so runtime comes from the output file's last write.
- The fold's table is `sum.tasks` (shells, monitors, workflow runs) with pending calls in `sum.task_calls`; rows keep `kind = "shell"` for shells and monitors (they share `shell_view`) and `kind = "workflow"` for runs.

**Workflow runs (`subagents.scan_workflow`, `agents/workflow_view.lua`)** (2.1.272, completed, failed and stopped runs)

- Launch result: `{status = "async_launched", taskId, taskType = "local_workflow", workflowName, runId, summary, transcriptDir, scriptPath}` — small, decoded in `settle_shell`. A `remote_launched` run has nothing local and is skipped.
- The agents are subagents of their own under `<session>/subagents/workflows/<runId>/` (`agent-<id>.jsonl` + meta with `agentType = "workflow-subagent"`, `description` = label, `workflowPhase`) — **not** the flat `subagents/` directory, so `scan` never lists them as orphans. Beside them `journal.jsonl` (`launched`/`started`/`result`/`failed` by `agentId`) is the only record that moves while the run does.
- `<session>/workflows/<runId>.json` (status `completed`/`failed`/`killed`, `error`, `logs`, `result`, `totalTokens`, `durationMs`, per-agent `workflowProgress` with `state` `start`/`progress`/`done`/`error`, `tokens`, `durationMs`) is written **only when the run ends**, every ending. The task's `tasks/<id>.output` is empty until then, so it is not used.
- Ends: a status notification (`Dynamic workflow "…" completed|failed: …|was stopped`, `<usage>` with `subagent_tokens`/`duration_ms`); a stopped run gets **no notification** (TaskStop result, `task_type = "local_workflow"`), but its record says `killed`. `workflow_state` precedence: notification → record → TaskStop → resume guess → live/recent (journal or agent transcripts written within `STALE_S`).
- `rows` walks sources by index because it grows them: each run's agent transcripts become sources with the agent as parent, so their shells and monitors nest under them. Agent rows are `kind = "subagent"` with `workflow`, `phase` and `path` (their transcript); state from the record's progress, else the journal, else the run's own state (a run that ended with an agent unfinished cut it off → stopped). `subagent_view.open` takes `path` (and threads it through `<BS>` history) for them. `refresh` folds the agent transcripts too.
- `workflow_view`: header, agents grouped by phase in journal order (each line `<CR>` → subagent float stacked on top), then Error (left out for `killed` — it is only the abort's stack), Result (pretty JSON, first 40 lines) and Log from the record. Repainted per 1s tick from the pane's rows (`opts.rows`), stopping one tick after the end. `tool_view` hands a `Workflow` launch to it, and a subagent transcript's Workflow call/notification lines route to it through `open_call`.
- **Foreground commands** (`subagents.foreground_output`; 2.1.272): a running foreground shell streams to `tasks/<id>.output` too, and the file is **deleted when the command returns** — but its id reaches the transcript only with the result, so the file is matched to the call. The call is written ~0.9s before the file is created (at spawn); a conversation's Bash calls run one at a time even when issued in parallel; overlap happens only across conversations (a subagent beside its parent). Matching: running = every pending `task_calls` entry across the session, its subagents and workflow agents (monitor/workflow launches not yet folded own unclaimed files too); unclaimed = files whose id is no task, notification or subagent of the session, created after the earliest running call − 2s; answered only for one-and-one, or equal counts paired by start order (`task_calls[].at` — the ISO timestamp's fraction, `_iso_to_epoch_precise` — against `_io.stat().birth`, the file's birthtime) with no file older than its call. Without birthtimes only one-and-one.
- `tool_view.open` on a running `Bash`/`PowerShell` call follows it in `shell_view` (`foreground = { output_path, started, tool, description }`, a row synthesized from the call). A float opened before the file exists shows "still running" and **retries** every `RETRY_MS` (`wait_for_output`): the file appearing upgrades it in place, the result landing shows the finished call. The live float hands off the same way (`handed_off`: `task_calls[tool_id]` gone after `subagents.refresh`) to `tool_view.open` with `reuse`; `on_handoff` rebinds the pane's stepping keys on the new buffer.
- **Every door opens it**: the Tasks row; `tool_view.open` delegates when `toolUseResult.backgroundTaskId` is set (so an Activity row does too, passing the command it already read); in a subagent transcript, `context` maps shells by tool_use id so the call line shows the shell's glyph (`in the background · exit N · 0:42`) and its `<task-notification>` line resolves to the shell rather than a subagent link, both routed by `open_call` on `call.shell`.

**Help (`?` / `keymaps.help`, `agents/help.lua`)**

- Lists the keys reaching the pane the cursor is in, grouped "this pane" then "anywhere in the view". A float via `snacks.win`, else `nvim_open_win`, into a scratch buffer we render and highlight ourselves so both paths match. A second `?` toggles it shut.
- Contents come from `KEY_SPECS`, the **same table `bind_keys` binds from**, filtered by pane and by what the user left bound.
- Headers/keys use `ClaudeCodeAgentsHelpHeader`/`ClaudeCodeAgentsKey` (linked to `Title`/`Special`, overridable via `agents.highlights.header`/`key`).

### 13. Floating Windows

Where a diff or file goes when there is no editor window: the agents tab (every window is an excluded pane) and `diff_opts.layout = "float"`.

- Floats **cascade** — each offset from the last, newest on top, title in the border, stack clamped so it never walks off screen. Several agents work at once and diffs arrive faster than you answer them; queueing would block a waiting CLI.
- Each carries `claudecode_live_preview` and `claudecode_float` so a second diff never targets the first's window.
- **The title says where the file is** (`utils.path_title`): the path relative to a root — the session's cwd for a pane float, the editor's own directory for a diff float unless a caller passes `root` — `~`-shortened when it is outside that root, with the note (`(vs HEAD)`, `·  <agent>`) after it. Fitted by the caller against `float.title_width()`, since Neovim cuts an over-long title at its **right** edge, which is the filename; `utils.shorten_path` drops interior directories instead. `diff.open_float` resolves the host module first so it fits to that module's geometry, not the global block's.
- `utils` owns `truncate`/`shorten_path`/`relative_path`/`path_title`; `agents/render.lua` re-exports the first three. They live in `utils` because `claude_agents.float` and `claude_agents.diff` need the same rules and core modules cannot require an opt-in feature.
- **The user's own display settings are applied, not inherited.** A float copies window-local options from the _current_ window, usually an agents pane with `wrap`/`number`/`list` off for fixed-width rows, and `style = "minimal"` wipes them again. `apply_user_options` runs after the window opens and puts the globals (`vim.go.*`) back on top. `fillchars` is left to `minimal` (frame chrome, not a reading preference).
- **A reused float is dressed again after every swap** (`reuse_window` → `apply_window_options`): putting a buffer in a `minimal` float re-applies minimal style (0.12.2), resetting `number` and `winhighlight`, so `<C-n>`/`<C-p>` stepping would lose the line numbers and the border colour. The border group is kept on the registry entry for the swap.
- **Every window option this plugin sets goes through `utils.set_win_option`, which passes `scope = "local"`.** `vim.wo[win].x = v` and `nvim_set_option_value(…, {win = w})` behave like `:set`, not `:setlocal`, when `w` is the current window — so they write the user's global. A pane is current while being built, so those forms would leak `wrap=false number=false list=false` into the user's globals.
- Geometry comes from the **top-level `float` block**, overridden by a feature's own table (`agents.float`), so `layout = "float"` does not take its geometry from a feature the user may have disabled. `config.validate_float` is shared by both blocks so key lists cannot drift.
- `agents/float.lua` is a thin wrapper supplying the session id, agents geometry and the `claudecode_agents_float` tag. **The stack is shared**, so agent floats and plain diff floats cascade past each other, and `diff.lua`'s cleanup closes a float through this module whichever door it came in by.
- **Terminal insert mode is restored**: entering a float leaves terminal-mode, so dismissing a diff would hand focus back in normal mode. The mode is read in `create` _before_ `nvim_open_win`, and the current window is only taken as the answer when it actually holds a terminal (`terminal_mode_window`) — a diff float is opened inside `nvim_win_call` (`diff.in_owning_tab`), which makes another window current while `mode()` still says `t`. `_setup_blocking_diff_unified` therefore reads the terminal _before_ entering `in_owning_tab` and passes it as `term_win`. Restore happens from a `WinClosed` autocmd (a float also goes away by `:w`, `:q` and a closing tab), then from `vim.schedule` (focus has not moved yet inside `WinClosed`), and only when the close actually returns to that terminal window.
- `bind_close` gives a float `q` and `<Tab>`. Because a float can hold a **real file buffer** (`open_file`), a mapping somebody else made is left alone, and ours are deleted on `WinClosed` — tied to the window, not to `M.close`, since `:q`, `<C-w>c` and a closing tab never reach it. Otherwise every file Claude showed you would carry a window-closing `q` forever.

### 14. Launch Profiles

`profiles = { default, list }`. Which account a Claude runs on, chosen per launch: `auth = "subscription"` or `"api"`, plus optional `model`, `args`, `env`, `workspace`, `mark`. Built-ins when `list` is nil: `subscription` (`s`) and `API key` (`a`, keychain entry `default`). A profile `key` may not be `h`/`j`/`k`/`l` or `q` (`profiles.RESERVED_KEYS`, config-validated): the menu binds profile keys `nowait` on its buffer, so one of those would take cursor movement or closing away from it. `default = nil` means plain launches are untouched (the CLI's own behavior). Entry points: `:ClaudeCodeProfile [name]` (tab; no name → menu), `ga` (`keymaps.new_as`) and `gi` (`keymaps.resume_as`) in the agents view, `:ClaudeCodeAgentNew [profile]`. No plugin-bound key. Typed in the agents view's tab, `:ClaudeCodeProfile` acts on the **selected session** (`agents_view.is_view_tab` → `resume_selected_as` / `resume_as_menu`), like every command typed from an agent's terminal: that tab has no Claude of its own, and starting one would split the view.

**What the CLI does with it** (2.1.300, print mode and interactive):

- An `apiKeyHelper` from `--settings` (file or inline JSON) outranks the claude.ai login: `/status` says `API key: apiKeyHelper`, the banner `API Usage Billing`, and there is no approval prompt. The workspace-trust gate applies only to a helper from project or local settings. The helper runs with `shell: true` (`/bin/sh`, `cmd.exe` on Windows); its output must be one printable-ASCII token; its stderr (≤500 chars) is shown as `apiKeyHelper failed: …`.
- `ANTHROPIC_API_KEY=""` and `ANTHROPIC_AUTH_TOKEN=""` launch on the subscription with no prompt: the CLI tests them for truth, and Neovim's job `env` cannot unset a variable. A non-empty key triggers "Detected a custom API key" (the answer is stored in `~/.claude.json` `customApiKeyResponses`). `--settings '{"apiKeyHelper":""}'` switches off a helper from the user's own settings.
- **A second `--settings` replaces the first entirely** — hooks and env — in either order. Hence `launch_settings` (below).
- A key in the environment reaches child processes (a hook sees it); a helper's key does not. The CLI's `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is opt-in and forces default permission mode.
- One conversation resumes across accounts, both directions, signed thinking blocks included.
- An organisation-level key (not workspace-scoped) gets `400 … must include the anthropic-workspace-id header`. `ANTHROPIC_WORKSPACE_ID` is federation-only; `workspace` is sent through `ANTHROPIC_CUSTOM_HEADERS` (`profiles.custom_headers`, merged with the user's own headers).
- An API launch switches off claude.ai connectors (the CLI warns).

**Launch seam** (`terminal.get_claude_command_and_env`, which every provider and `registry.launch` go through): session flags first, then `profiles.resolve(explicit, argv)` — the profile asked for, else the one the resumed conversation (`--resume`/`-r`/`--session-id` in the command) last ran under, else the default — then `profiles.launch_parts`: `--model` (unless the command has one), `args`, env (both auths blank `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`, `api` also `CLAUDE_CODE_OAUTH_TOKEN`; profile `env` over that), and settings (`apiKeyHelper`: the helper for `api`, `""` for `subscription`; the same blanks in settings `env`, which outranks the user's settings). Then `launch_settings.apply`.

**`launch_settings`**: one `--settings` per launch. The user's own flags (`--settings X`, `--settings=X`, inline JSON or a path relative to the spawn cwd) are read — the last one, as the CLI would — and removed; the plugin's hooks are **appended** per event to theirs; the profile's `apiKeyHelper` and `env` entries win. Untouched when neither hooks nor profile add anything. An unreadable user file is logged and left out. Written through `live_cursor.write_settings_file` (cleaned up with the rest).

**The key** (`api_key.lua`, run by `scripts/api_key.lua` as `nvim --headless -u NONE -l … get <entry>`): read from the OS keychain by the helper process, never by Neovim. macOS `security find-generic-password -s claudecode.nvim -a <entry> -w` (exit 44 = missing); Linux `secret-tool lookup service claudecode.nvim account <entry>`; Windows Credential Manager target `claudecode.nvim/<entry>` via LuaJIT FFI `CredReadW` (`cmdkey` stores UTF-16LE; `decode_blob`; untested on Windows). `check <entry>` / `check-cmd <cmd>` print `found <len> <shape>` or `missing`, never the key — used by `:checkhealth` (`profiles.check_sync`) and the menu (`profiles.check`, async). A missing key's message is the exact store command (`api_key.store_command`, hidden-input tools). Entry names are `[%w._-]+` (config-validated) since they go on the command line unquoted.

**Per conversation** (`stdpath("cache")/claudecode/profiles.json`, the flags store's robustness via the shared `store_io`: libuv-only I/O, read-before-write, rename into place; `profiles.refresh()` one stat per list refresh, `of()` asks nothing of the disk since a list paint calls it per row). Recorded by `registry.launch` (agents), by `note_tab_terminal` (a tab's terminal when it appears, with the id the command named), and on `SessionStart` (`note_tab_session` for a tab's Claude; `registry.rekey` for an agent's `/clear`). `model.delete_sessions` forgets. Session restore needs nothing extra: a resumed id finds its own profile.

**Tab tracking**: `get_claude_command_and_env` sets `set_pending_tab_launch` on every build (toggles rebuild the command whether or not a process starts); `tag_terminal_tab` turns it into the tab's profile only when a new terminal buffer appeared. `TermClose` (unless restarting) → `forget_tab`. The `TermClose` watcher is registered unconditionally, since profiles always exist.

**Switching a running Claude** restarts it with `--resume`, after a confirmation only when it is `busy`/`waiting`. The old CLI is **stopped and waited for** (`terminal._stop_and_wait`: `jobstop`, `TermClose` on that buffer, `sigkill` after `_restart_grace_ms`) before the new one starts — two CLIs on one transcript interleave writes. Tab: `terminal.restart` marks `restarting[tab]` so the `TermClose` watcher forgets nothing, deletes the dead buffer so the provider opens a fresh one; needs the conversation id from `status` or session persistence; refused for the external provider. Agents: `registry.relaunch` marks `term.relaunching` (so `note_terminal_closed` shows no "ended" screen), and `agents_view.resume_as` first puts a "Switching to …" notice in the centre — **deleting the old terminal's buffer closes the window showing it**, and that window is the centre pane the new terminal needs. A conversation running in another tab is left there.

**UI**: `profile_menu.lua` (core, since the tab path uses it), single-key like `gs`, floated through `menu_float.lua` (shared with `sort_menu`). API rows say `checking key…` / `no key stored` / `key check failed` as the async check lands; a profile whose key is known missing is refused with the store command (`profiles.refuse_if_missing`). Rows of sessions run on an API key carry the profile's mark (`$` default for `api`, `ClaudeCodeProfileMark` → `Special`) after the flag and worktree marks; the centre's offer says `last ran under <profile>` and `i` uses it. A follow-up (`A`) runs under its session's profile.

**OpenCode profiles**: `backend = "opencode"` with optional `model` (`provider/model`, validated), `agent`, `args`, `env`, `mark`; `auth`/`keychain`/`api_key_cmd`/`workspace` are refused on them, and `agent` on a Claude one. `profiles.builtin_list(config)` adds `OpenCode` (`o`) when OpenCode is the backend or its executable is on PATH, and drops the Claude built-ins only when OpenCode is the backend and `claude` is not executable. `launch_parts` for an OpenCode profile blanks nothing (OpenCode keeps its own credentials) and returns `model = { providerID, id }` and `agent`, which go on the session through the API — the TUI has no flag for either. `session_of_argv` also reads `--session`/`-s <ses_…>`. A Claude profile remembered for or defaulted on a launch that runs OpenCode is ignored there.

### 15. OpenCode Backend

`backend = "claude" | "opencode"` (default `"claude"`), `opencode = { cmd, review_edits = true, service_timeout_ms }`, `command_aliases`, `status.opencode_icons`. Verified against OpenCode **2.0.30** (V2); modules under `lua/claude_agents/opencode/`, plus `backend.lua` and `agents/opencode_store.lua`. `scripts/opencode_smoke.lua` drives all of it against a real service (`nvim --headless -u NONE -l scripts/opencode_smoke.lua [model]`, haiku by default, temp repo, deletes its sessions; `SMOKE_DUMP=<file>` keeps the written transcript and the fold).

**Which CLI** (`backend.resolve`): the explicit profile's backend, else the backend of the conversation the launch names (`ses_…` = OpenCode, UUID = Claude; from `launch.session_id` or the command line), else the tab's session-persistence record, else `profiles.default`'s, else `backend`. Called at the top of `get_claude_command_and_env` after the instance is ensured, inside a `pcall` that falls back to Claude — an error there must never cost a Claude launch. A conversation only continues in the CLI that holds it: `terminal.launch_profile` and `agents_view.resume_as` offer a new conversation instead when the profile is on the other backend.

**OpenCode's shape**: a full-screen TUI (OpenTUI) that is a client of one background **service** per user; the service owns sessions (SQLite, read only through the API — never touch the DB), config, plugins and tools. The main TUI takes `--session <id>` (continue, or create), `--continue`, `--prompt`, `--auto`, `--standalone`, `--server` — **no `--model`/`--agent`/`--fork`** (only `opencode mini` has them). `OPENCODE_CONFIG_CONTENT` is read by the _server_ process, so it never reaches the shared service from a launched TUI.

**Service** (`opencode/service.lua`): `<state>/service.json` = `{ id, version, url, pid, password }`, `<state>` from `opencode debug paths state` (starts nothing; asked once). HTTP Basic, user `opencode`; Bearer is refused. `ensure` probes `/api/info` and runs `opencode service start` when nothing answers (waiters share one attempt); `find` never starts it. **Only a launch may start the service**: `api.call{no_start = true}`, the event stream and the agents store all use `find`, so having OpenCode installed starts nothing for a Claude-only user. A disabled service (`opencode service set disabled true`) leaves TUIs on private servers the plugin cannot reach; `:checkhealth` warns.

**HTTP** (`opencode/http.lua`): pure `vim.loop`, `Connection: close`, Content-Length / chunked (three-phase dechunker: size line, data, CRLF — a chunk split anywhere, including inside its CRLF) / EOF; SSE parser (`data:` lines joined by `\n`, `:` comments skipped). `request_sync` waits with `vim.wait` — main loop only. `vim.json.decode` with `luanil` so `null` is nil. An empty table body is sent as `{}`.

**Editor context**: the TUI's built-in `EditorContext` speaks the IDE protocol: port from `CLAUDE_CODE_SSE_PORT` (read first) or `OPENCODE_EDITOR_SSE_PORT` — the launch sets **both** to the instance's port, so an inherited one cannot point it elsewhere. With the port from the env it connects **without the token** (it sends a lock file's token only when it found the editor by scanning `~/.claude/ide/*.lock`: transport `ws`, workspace folder containing cwd, longest match then newest mtime — wrong tab/agent with several in one project, hence the env). It sends `initialize` (protocol `2025-11-25`) and `notifications/initialized` and calls **no tools**; `selection_changed` becomes a footer label sent as a synthetic "editor context" message before the next prompt, `at_mentioned` a mention in the prompt. The **tokenless door**: `server/init.lua` `arm_tokenless(on)` and `tokenless_allowed(clients)` (armed, and no other live tokenless client); `handshake.validate_upgrade_request`'s third argument is consulted only when the auth header is missing and **never when an `Origin` header is present** (every browser sends one); the client is marked `tokenless` and `tools/list` answers `[]`, `tools/call` -32601. Armed by `launch.started` (the process exists), disarmed by `launch.ended`. A sent token is still checked.

**Sessions** (`opencode/sessions.lua`): ids are minted the way OpenCode does (`opencode/ids.lua`: `ses_` + 12 hex + 14 base62; hex = `(2^48-1) - ((ms mod 2^36)*4096 + counter)` — newest sorts first; exact in doubles; checked against real ids). The TUI creates an unknown `--session` id **only when the first prompt is submitted** (pty probe) and by then the prompt runs — too late for a profile's model or the review rules — so `ensure_sync` runs **while the launch is built**: GET; 404 → POST `{ id, location = { directory = canonical cwd }, model, agent, title, metadata.claude_agents }`; existing → `set_model`/`set_agent` if the profile asks; then `apply_rules`. `ready[id]` makes a toggle's rebuild ask nothing; `closed(id)` (terminal closed, not restarting, not shutting down) deletes a session **this Neovim created** that holds no user/assistant message; `relaunching(id)` only clears `ready`. `resumable(id)` (a user message exists; sync, 2s) is session persistence's `transcript_exists` for `ses_` ids. **Directories are canonical** (`opencode.canonical`, `fs_realpath`): the TUI process sees the real path and moves a session it opens under another spelling (macOS `/var` → `/private/var`).

**Launch** (`opencode/launch.lua`): `<opencode.cmd> [args] --session <id>`; `--resume/-r/--session-id <ses_…>` in the args (Claude's words, from `terminal.restart` or a user) become `--session`; a command with `--session`/`-s`/`--continue`/`-c` is left alone. A tab's id: session persistence's `session_state.opencode_session(tab, cwd)` (mints `ses_`, treats a Claude record as the fallback — and `launch_args` does the reverse), else `tab_ids[tab]`, kept while the process lives so toggles do not mint another; cleared on `TermClose` (`init.lua` watcher reads `b:claudecode_opencode_session`). Env: config `env`, both port variables, profile env, `no_proxy` with loopback. No `ENABLE_IDE_INTEGRATION`/`FORCE_CODE_TERMINAL`/hook settings. `launch.started` (from `tag_terminal_tab` for tabs, `registry.launch` for agents) arms the door, `bridge.track`s the session, remembers the profile. `send_newline` sends `\n` (Ctrl+J) when `b:claudecode_backend == "opencode"` — OpenCode's newline keys are shift/ctrl/alt+return and ctrl+j, and a backslash is text.

**Events → hooks** (`opencode/bridge.lua`): one SSE subscription (`opencode/events.lua`, `GET /api/event`, `{ id, created, type, location, data, durable }`; volatile — reopened with backoff, each open announced as `stream.connected` → `resync`: GET `/api/session/active` ends turns that finished in the gap, `review.resync` opens permission requests asked in it). Only tracked sessions: launched roots plus children (`session.created` with a tracked `parentID`; root, tab and agent key inherited). Translation — `session.execution.started` → `UserPromptSubmit` (root only); `session.tool.called` → `PreToolUse` (**the tool name is not on it**: it arrives on `session.tool.input.started {id, name}` and is remembered by call id); `session.tool.success|failed` → `PostToolUse` with `tool_response = { filePath, structuredPatch }` from the result's patch; `permission.asked` → `PermissionRequest` with `tool_use_id = source.id`; `form.created` (the question tool, `data.form.metadata.tool.id`) → `PermissionRequest` for `AskUserQuestion`; `execution.succeeded` → `Stop` (child: `SubagentStop`), `failed` → `StopFailure`, `interrupted` → `status.note_interrupt(tab)` + `model.note_interrupt(root)`; `session.deleted` → `SessionEnd`; track → `SessionStart`. A child's events carry `agent_id = <child id>` and `session_id = <root>`, so a subagent's question stays its own thread (`status.advance`). Every synthesized event carries `opencode = true` (`agents_view.note` classifies them whatever `agents.source` says — the stream reports every end) and `transcript_path = opencode://<root>.jsonl`. Tool names/inputs mapped by `opencode/tools.lua` (`read`→`Read`, `edit`→`Edit`, `write`→`Write`, `shell`→`Bash`, `subagent`→`Task`, `question`→`AskUserQuestion`, …; `path`→absolute `file_path`, `oldString`→`old_string`). A successful Write/Edit under `~/.opencode/plan/` shows the file in the plan view (tabs only; no approval step; closed by the next `PreToolUse`). `interrupt_watch.arm` ignores `ses_` ids.

**Review** (`opencode/review.lua`, `opencode/rules.lua`): OpenCode's default policy allows every edit, so review needs session rules — but **session rules are evaluated after the agent's and the last match wins**: a bare `edit * ask` turns every deny into an ask (the plan agent's, `explore`'s `* * deny`, a user's own). `rules.compose(current, previous, agent_rules)`: the session's non-plugin rules, then `{edit,*,ask}`, then every agent rule whose action wildcard-matches `edit` **except catch-all allows**, each rewritten to action `edit` (a copied `* * deny` must not reach other actions). Agent rules from `GET /api/agent/<id>?location[directory]=` (effective ruleset); default agent from `GET /api/config` `default_agent`. Recomputed on `session.agent.selected` and a child's creation (children inherit the parent's rules at creation). What the plugin added is recorded in `metadata.claude_agents.rules` and is always the tail, so a recompute replaces exactly it; `review_edits = false` strips it. Unreadable agent rules → nothing changed. `permission.asked` (`action = "edit"`, `metadata.files[] = { file, patch, status, additions, deletions }`): each file's proposal = `tools.apply_hunks(disk, hunks)` (checked against context; a mismatch leaves the request to the TUI); one diff per file through `diff.open_review` (the callback counterpart of `open_diff_blocking`: same setup functions, no coroutine; `request_context` set from the tracked entry first, so placement follows the agent/tab), named `✻ [OpenCode] <rel> (<req tail>) ⧉`. All saved as proposed → `once` + `finish_review` (waits for OpenCode's write like close_tab); any saved changed → the plugin writes every file and replies `reject` with `APPLIED_OWN`; any `:q` → `reject` `REJECTED`, others `dismiss_review`. Reply `POST …/permission/<id>/reply {decision, message}` (204). A `permission.replied` this Neovim did not send → `dismiss_review` (answered in the TUI). A session ending → its reviews dismissed.

**Agents view** (`agents/opencode_store.lua`): each OpenCode session is written out **as the Claude transcript it would have been**, in memory, and served through `transcript._io` (`stat`/`read`/`read_sync`/`read_tail_sync`/`scandir` branch on the `opencode://` prefix) at `opencode://<id>.jsonl` — named like a transcript so `new_summary`'s id and `subagents.dir` read it unchanged. Public functions that must fetch first go through `when_current` (`summary`, `file_history`, `tool_call`, `search`); `stale` also asks `store.outdated`; `list`/`list_all` append the store's rows; `session_path`/`locate` answer `ses_` ids directly; `cwd_of`, `delete` (API DELETE) branch. The written transcript **only grows** (the incremental fold's assumption): a call's `tool_use` line when it appears, its result when it is completed/error, text/reasoning when the message completes, `idle {outcome = interrupted}` → the interrupt marker, the session title as `ai-title` lines (last wins). A revert (session `revert` changed) rewrites it under `gen + 1` (the fold's `ino`). Results in Claude's shapes: edit `{filePath, oldString, newString, structuredPatch}` from the result's patch (**V2: `metadata.files[1].patch`**, V1: `diff`/`filediff`; `tools.metadata_patch`), write create/update, read `{type="text", file={…, totalLines=-1}}` (never a whole-file anchor), shell `{stdout}`, subagent `{agentId, totalDurationMs, totalTokens}`, patch tool → one Edit per file; a `permission.rejected`/`aborted` error is written with `REJECTION_MARKER` (a declined non-file tool reads ⊘; a declined file tool leaves no row, as for Claude). Fetch: everything once (`order=asc`, `cursor.next`), then the newest page (`order=desc`, 20) back to the first message already complete. Dirty on the session's events (`MOVES`), on `stream.connected`, and when the list's `time.updated` moves. Subagents: a `subagent` part's `metadata.sessionID` registers the child under its root with a Claude-shaped descriptor (`agentType`, `description`, `toolUseId`, `parentAgentId`, `requestShape`), listed at `opencode://<root>/subagents/agent-<child>.{meta.json,jsonl}`; the child's own transcript is written the same way. Listing: `GET /api/session?parentID=null&limit=100&order=desc` by `project` (from `GET /api/location`), or — for the `global` project — by directory **under both spellings** (cwd and its real path), merged; refreshed every 3 s or when dirty, a changed answer calls `model.refresh_list`. Rows get the `◇` mark (`opencode.MARK`) unless a profile gives one.

**Status icons**: `status.OPENCODE_SPINNER` = OpenCode TUI's own braille snake `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` (`uD` in the 2.0.30 binary). `icon_spec(state, session_id)`: a `ses_` conversation reads `opencode_icons[state]` first, busy defaulting to the snake; other states fall back to `icons`. `icon(tab)` passes the tab entry's `session_id`; `icon_for_state`/`is_animated` take the row's session id. Paced by the one shared clock (`spinner_ms`), not OpenCode's 80 ms.

**Other seams**: `registry.launch` for a `ses_` id: `--session <id>` (fork mode: `POST /api/session/<id>/fork` first, launching the copy — the bridge's `SessionStart` for it rekeys the agent like a Claude fork's), the name goes to the session title, `term.backend = "opencode"`, `launch.started` with the agent key, `launch.ended` on exit/stop (`keep` while relaunching). `agents_view.start_agent` mints the id for the backend the launch will run. `:ClaudeCodeSelectModel` with OpenCode lists `GET /api/model` and switches the running tab session (`POST …/model`) or launches with `launch.model`. `terminal/native.lua` and `selection.lua` recognise `opencode` terminal buffers too; `terminal_links` stays Claude's (OpenCode prints no OSC 8). `:checkhealth` has an OpenCode section (binary, version, service, disabled service, review, the tokenless door) and a missing `claude` is only info when OpenCode is the backend. Not done: the plugin's MCP tools for OpenCode; following a session started in the TUI with `/new`.

**Keys in an OpenCode agent's terminal**: the agents view binds `agents.keymaps.next_session`/`prev_session` (`<C-n>`/`<C-p>`) in terminal mode on every agent terminal (`map_cycle`), so OpenCode never receives them there — and OpenCode 2.0.30 opens its command palette with ctrl+p (`command.palette.show`; ctrl+n/ctrl+p are also list/autocomplete alternatives to the arrows). `opencode.agent_keybinds()`: nil config → `{ ["command.palette.show"] = "<leader>p" }` while either session key is `<C-p>` (`opencode_key` maps `<C-x>`/`<M-x>` to `ctrl+x`/`alt+x`); `false` → nothing; a table → exactly it. `launch.build` merges it, for agent launches only (`not ctx.for_tab`), into `OPENCODE_CLI_CONFIG_CONTENT` (OpenCode's inline `cli.json`, read by the **TUI** process, so per launch — verified in a pty: ctrl+p stops opening the palette, the new key opens it) over whatever the variable already held (config `env`, then the process environment). Tab terminals are untouched: nothing takes ctrl+p there.

**Command aliases** (`command_aliases = true`): `init.alias_name` (`ClaudeCode`→`Agent`, then `AgentAgent`→`Agent`); `_create_commands` records each `nvim_create_user_command` call made by `create_commands` and re-creates it under the alias with the same function and options, skipping names another plugin owns (`nvim_get_commands`, `exists(":")`), redefining its own (`M._aliases`).

### WebSocket Server Implementation

- **TCP Server**: `server/tcp.lua`. Port selection has two non-obvious constraints:
  - **`bind()` does not prove a port is free**: libuv sets `SO_REUSEADDR` on every TCP bind, and on macOS the bind succeeds even when another process is listening — only `listen()` reports the conflict. `_port_is_free` binds _and_ listens; `create_server` skips the probe entirely, binding and listening on the real socket and moving to the next candidate (up to `MAX_BIND_ATTEMPTS`) rather than failing the start.
  - The candidate shuffle is seeded in `server/utils.lua` mixing pid and `vim.loop.hrtime()` — `os.time()` alone has one-second resolution, so two Neovims started in the same second would pick the same port.
- **Handshake**: `server/handshake.lua` — HTTP upgrade with authentication.
- **Frame Processing**: `server/frame.lua` — RFC 6455 frames.
- **Client Management**: `server/client.lua`.
- **Utils**: `server/utils.lua` — base64, SHA-1, XOR in pure Lua.

#### Authentication

- **128-bit tokens**: 32-char lowercase hex from the OS CSPRNG, per session.
- **Header**: `x-claude-code-ide-authorization`.
- **Discovery**: tokens stored in `~/.claude/ide/[port].lock`.
- Server accepts only local connections (127.0.0.1).

### MCP Tools

All tools return MCP-compliant `{content: [{type: "text", text: "JSON-stringified-data"}]}` and match the VS Code extension's behaviour and output.

**MCP-exposed** (with JSON schemas): `openFile` (optional startLine/endLine, preview mode, text pattern matching, makeFrontmost), `getCurrentSelection`, `getLatestSelection`, `getOpenEditors` (VS Code-compatible `tabs` structure), `openDiff`, `checkDocumentDirty`, `saveDocument`, `getWorkspaceFolders`, `closeAllDiffTabs`, `getDiagnostics`.

**Internal** (not exposed): `close_tab`.

Tools with `schema = nil` are internal-only; see `lua/claude_agents/tools/init.lua` for registration.

- JSON payloads are encoded compactly — no `indent`, which only spends tokens.
- `getDiagnostics` answers in VS Code's shape: one text block holding `[{uri, diagnostics: [{message, severity, range, source, code}]}]`, grouped per file, with **LSP ranges** (0-based lines and characters) and severity **names**, not Neovim's numbers. Claude parses that shape.
- `openFile` applies its selection inside the window the file landed in, which is not the current one for a background open (`makeFrontmost = false`) or a float.
- A path is expanded with `utils.expand_tilde`, never `vim.fn.expand`, which reads `$name` as an environment variable and drops undefined ones — mangling a literal `$` in a path (`src/routes/$post.tsx`). `:ClaudeCodeAdd` still expands the `%`/`#`/`<cfile>` token forms, since `:ClaudeCodeAdd %` is the documented "add this buffer" keymap.
- The `initialize` response advertises no `resources` capability: we implement none.

## Testing Architecture

Two layers (plus a few older top-level `tests/*_test.lua` files):

- **Unit** (`tests/unit/`) — individual functions and subsystems in isolation, against `tests/mocks/`
- **Integration** (`tests/integration/`) — end-to-end with a mock Claude client

Files match `*_spec.lua` / `*_test.lua`, busted framework. Custom JSON encoder/decoder in `tests/busted_setup.lua` handles nested structures, Lua keywords as keys (`["end"]`), and MCP message validation.

Principles: isolation (no external state), comprehensive vim-API mocking, positive/negative/edge cases, fast execution, descriptive names.

**Tool test pattern**:

```lua
local result = tool_handler(params)
expect(result).to_be_table()
expect(result.content).to_be_table()
expect(result.content[1].type).to_be("text")
local parsed = json_decode(result.content[1].text)
```

**Error format**:

```lua
error({
  code = -32602,  -- Invalid params
  message = "Description of the issue",
  data = "Additional context"
})
```

### Authentication Testing

- `tests/lockfile_test.lua` — token generation/uniqueness, lock file creation, reading tokens, missing/invalid token handling
- `tests/unit/server/handshake_spec.lua` — valid/invalid/missing tokens, empty tokens, malformed headers, length limits, case-insensitive headers
- `tests/unit/server_spec.lua` — startup with tokens, token state across lifecycle
- `tests/integration/mcp_tools_spec.lua` — full auth flow, persistence across operations, concurrent operations

Manual checks:

```bash
# Auth token from lock file
cat ~/.claude/ide/*.lock | jq -r .authToken

# Should succeed
websocat ws://localhost:PORT --header "x-claude-code-ide-authorization: $(cat ~/.claude/ide/*.lock | jq -r .authToken)"

# Should fail
websocat ws://localhost:PORT --header "x-claude-code-ide-authorization: invalid-token"
websocat ws://localhost:PORT

# Interactive script reads the token automatically
cd scripts/ && ./claude_interactive.sh
```

Log levels: DEBUG for successful auth/connection/handshake detail, WARN for handshake auth failures, ERROR for token generation and handshake response errors. Use INFO sparingly, only for events users need to know about.

## Development Notes
